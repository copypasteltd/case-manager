# 文档基线、范围与执行规则

版本：v1.0-draft；日期：2026-10-23；状态：可审阅的开发设计基线，尚未获得业务签核，尚未实现产品。

## 1. 如何使用本套文档

本套文档将原有 v0.2 可行性方案展开为需求、开发契约、质量、运维与交付约束。文档版本号不代表产品已经发布。原 `00`—`07` 文件保留立项论证与来源；细化设计以本套目录中的新文档为准，已确认用户要求始终优先。

| 层级 | 作用 | 主要读者 |
| --- | --- | --- |
| governance | 确认范围、用语、决策、配置与变更规则 | 负责人、产品、架构、测试 |
| requirements | 可观察业务行为、状态、异常与验收条件 | 产品、业务、前后端、测试 |
| development | 数据、接口、任务、存储、客户端与 AI 契约 | 开发、架构、运维 |
| quality | 测试、需求追踪与上线证据 | 测试、业务验收人 |
| operations | 部署、迁移、备份与故障恢复 | 运维、开发 |
| delivery | 依赖、工作包与完成标准 | 项目负责人、全体执行人员 |
| templates | 新需求、决策、接口变更与验收记录格式 | 全体贡献者 |

全部项目说明、计划、接口说明、报告、会议结论和模板必须放在 `docs/`；实际源代码、迁移脚本与自动生成程序产物将来可按工程目录组织。文档不得包含真实密码、Token、银行卡完整信息、客户敏感原文或生产连接串。

## 2. 来源与规范用语

- **U（已确认）**：用户原话或明确回复，关联原 `U-01`—`U-20`。除非用户变更，不得擅自缩小。
- **D（设计约束）**：本套文档提出的工程方案。实现时必须遵守；若要偏离，先补决策和影响分析，而不是默默换方案。它不等于公司已经批准投入或经营规则。
- **A（候选参数）**：性能、容量、价格和默认值估算；只能用于开发/压测或预算模型，不能冒充实测或 SLA。
- **Q（待决策）**：缺失输入，见 [决策登记](02-decisions-and-open-questions.md)。关联功能可以先开发，但涉及真实业务的放行取决于登记的门槛。

正文“必须/不得”为约束，“应”为有理由可偏离的建议，“可”为可选能力。“已完成”仅用于有持久化业务证据的操作；受理、上传、复制、批准、付款分别表达，不混用。

文档冲突按“用户最新明确要求 → 已签核变更 → 本基线中的细化契约 → 原可行性建议”处理。冲突无法直接消解时登记问题，未确定的高影响业务动作保持拒绝；其余独立工作继续。

## 3. 已确认基线与首发范围

| 事项 | 固定输入 |
| --- | --- |
| 服务对象 | 单公司内部使用，3 名员工、3 人同时在线，香港使用 |
| 服务器 | 已有境内云服务器；厂商、OS、规格、网络与账号稍后提供 |
| 技术 | Go + PostgreSQL；React + Vite 管理门户；Taro 微信、抖音、Android；Codex 秘书；Telegram Bot |
| 文件 | 原件约 2 TB；最大单文件 120 GB；精确计量保存字节数 |
| 上传分工 | Web/Android 承担 120 GB；小程序承担查阅、审批及经验证的普通附件 |
| 业务 | 合同、报销、采购、月度开支/订阅；项目完整闭环、文件、项目博客、服务状态 |
| 存储 | OSS 与 R2 两份；应用节点仅临时目录/缓存；数据库必须独立持久化 |
| 交付 | Web、微信、抖音、Android 必须同批正式首发；阶段开发不构成减少首发平台 |
| 执行环境 | 严禁调度本地 Docker、WSL、虚拟机、设备模拟器等虚拟化环境；使用原生工具和 Android 真机；浏览器调用后关闭不用标签页 |

当前不纳入：考勤、人事、薪酬、iOS、会计总账、资金自动执行、电子签约、多人 Office 协作、复杂资源排程、公开客户门户、公开博客、任意 SSH 和自动生产修复。新增范围进入变更流程。

“完整项目管理”的最低闭环固定为：立项/范围 → 成员/任务/依赖/里程碑 → 文件/日志/合同 → 预算/实际成本 → 风险/问题/变更 → 交付/验收 → 归档/复盘。不能用只有任务看板的版本替代。

## 4. 跨模块不可破坏的约束

1. Go 业务层统一鉴权和正式业务写入；客户端、模型、Skill、TG 均不能直接写数据库或正式对象。
2. 默认拒绝。管理员配置权限不自动包含全部合同/费用/文件阅读权限。每次列表、数量、检索、引用和下载都检查实际资源范围。
3. 文件内容不可变；文件 ID、版本 ID、上传会话 ID、对象 Key 是不同概念。新版本成功必须以数据库正式提交为准。
4. 审批实例固定提交内容、流程版本和审批人；提交后不得直接覆盖内容。审批结果与验收、履约、付款等业务事实分离。
5. 实际费用只登记一次，其他模块通过关联使用；金额定点数、币种和汇率快照必须明确。
6. 正式写入采用并发版本与幂等；异步处理至少一次投递，消费者必须幂等，跨云不承诺天然原子或恰好一次。
7. AI 的有效权限为调用人、资源范围、渠道和任务授权的交集；撤权后新工具拒绝，旧上下文不得继续泄露。
8. 业务事实、任务、授权与审计不能只存在应用本机。双对象副本不替代数据库备份。
9. 自动故障恢复不能制造双主写入。主端切换必须使用存储纪元和旧端隔离。
10. 生产首发必须逐端、逐业务验收；未执行的测试标记“未执行”，不以文档完整度替代产品可用性。

## 5. 编号与变更管理

新详细需求使用 `PRD-* / IAM-* / PM-* / OA-* / FIN-* / FILE-* / AI-* / OPS-* / NFR-*`；质量用 `TC-*`；工作包 `WP-*`；待决策 `Q-*`。原 `U-* / R-* / ADR-* / AC-*` 保留，不能重新赋义。

每项范围变更记录：触发原因、旧/新行为、受影响需求/数据/API/客户端/Skill/测试、迁移与回退、工期/费用、决策人和日期。变更未确认前按现基线继续；若冲突涉及权限、费用、删除和对外披露，则仅暂停冲突动作。

设计完成的证据是状态机、数据约束、错误契约、至少一条正常及异常验收路径均齐备。业务规则冻结另需负责人确认。开发完成还需实现与测试证据，见 [交付计划](../delivery/01-work-packages-and-gates.md)。

## 6. 术语

| 术语 | 定义 |
| --- | --- |
| 申请修订 | 一次提交的业务内容快照；退回修改会产生新修订 |
| 审批实例 | 对特定修订运行的一次固定流程；不与其他修订共用审批结果 |
| 实际费用 | 已核实发生的支出事实；不等于已付款 |
| 付款记录 | 人工登记的实际现金动作；不意味着系统发起转账 |
| 原件版本 | 一份不可变的文件字节；恢复旧版也生成新的正式版本 |
| 可用 | 主端文件已检验并正式提交，授权用户可以访问 |
| 副本已校验 | 副本字节数与指定内容摘要匹配，有校验证据 |
| RPO/RTO | 允许丢失的数据时间窗口/恢复目标时间；按故障域分别定义 |
| 秘书任务 | 一次有身份、范围、预算、Skill 版本和可追踪结果的执行 |
| 计划授权 | 对固定操作列表、内容摘要与版本的批准或既有授权匹配结果 |
