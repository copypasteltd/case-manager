# 文件存储、双云备份与恢复

日期：2026-10-22。版本：v0.2。基线：约 2 TB 原件、最大单文件 120 GB；香港员工访问境内服务器；Web/Android 上传大文件，小程序查阅与审批。

## 1. 推荐策略

采用 **一个活动主存储 + 一个跨云副本 + 应用级不可变版本 + 独立数据库备份与恢复清单**。暂定境内 OSS 为活动主存储、R2 为副本，最终根据香港访问、境内跨云复制和费用实测确定。

不建议首期做两个对象存储同时接受业务修改的双主架构。主存储成功即可进入已上传状态；副本必须复制并校验后才显示“已双云备份”。高价值签署件可配置为双副本完成后才允许进入归档确认状态。

3 人在线不能降低对 120 GB 上传、2 TB 首次迁移和跨云数据校验的要求。对象存储负责大文件字节；应用服务器只保存有上限的分片缓冲和任务元数据。

## 2. 官方能力边界

| 问题 | 核实事实 | 本项目处理 |
| --- | --- | --- |
| OSS 能否存 120 GB 文件 | 支持分片/断点上传；普通单次上传不是适用方式 | 用 Multipart，不能把普通上传接口直接放大 |
| R2 能否存 120 GB 文件 | 容量处于其分片对象限制内；存在分片大小、数量限制 | 采用 S3 Multipart 与已验证的分片策略 |
| OSS 原生 CRR 能否直达 R2 | 官方 CRR 描述的是 OSS Bucket 间复制 | 自建或集成跨云复制 Worker，按应用清单驱动 |
| R2 是否等同完整 S3 | 官方有 API 兼容清单；部分版本/复制 API 不支持 | 核心版本由应用维护；独立存储适配器 |
| R2 是否可精确保证地理城市 | Location Hint 是尽力提示，jurisdiction 是另一个约束 | 不把 APAC 提示等同香港机房；严格两地条件单独核实 |
| R2 能否直接用自定义域名签名 URL | S3 预签名 URL 适用 S3 API 域名 | 私有下载用有效的 API 签名或鉴权代理，不公开 Bucket |

来源：[OSS 上传方式](https://www.alibabacloud.com/help/en/oss/user-guide/upload-objects-to-oss/)、[R2 限制](https://developers.cloudflare.com/r2/platform/limits/)、[R2 分片上传](https://developers.cloudflare.com/r2/objects/upload-objects/)、[OSS CRR](https://www.alibabacloud.com/help/en/oss/user-guide/cross-region-replication-overview/)、[R2 S3 兼容](https://developers.cloudflare.com/r2/api/s3/api/)、[数据位置](https://developers.cloudflare.com/r2/reference/data-location/)、[预签名 URL](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)。核实于 2026-10-22。

“双云”可以降低供应商故障相关性，但不自动证明具体地理隔离、数据出境要求或管理员失误隔离。云区域、账号归属、客户资料分类和跨境处理范围应写入正式配置清单。

## 3. 文件与目录模型

目录是 PostgreSQL 中的逻辑树，文件 ID 和版本 ID 是稳定标识。对象 Key 使用不含客户姓名、合同标题等敏感信息的稳定 ID，例如：

```text
org/{organization_id}/files/{file_id}/versions/{version_id}/original
org/{organization_id}/derived/{version_id}/{derivative_id}
backups/postgres/{backup_id}/...
backups/catalogs/{catalog_id}/manifest.json
```

重命名或移动目录只改变逻辑关系，不复制 120 GB 对象。更改内容产生新版本，不原位覆盖正式对象。大二进制文件只改一个字节也可能需要新增整个对象版本，应在界面提示额外存储与复制成本。

应用级版本不依赖 R2 原生 S3 版本功能。OSS 原生版本如启用，定位为附加保护，并计入独立容量预算，避免在应用版本之外无计划保留多份副本。

## 4. Web/Android 120 GB 上传

### 4.1 上传流程

1. 客户端提交文件名、大小、类型、项目和目标逻辑目录，后端检查账号、配额与目录权限。
2. 建立持久化上传会话，记录文件指纹、目标草稿 Key、存储端 Multipart ID、分片大小、分片数量与过期策略。
3. 客户端分片直传主对象存储；后端按需签发限定分片的短时凭证。长任务可经重新鉴权刷新，不能因为一个短时凭证过期而重传整文件。
4. 客户端与后端记录已确认的分片，恢复时与存储端实际分片对账。只重试缺失或不一致的分片。
5. 完成请求核对分片清单与总大小；服务端完成合并并进入校验/扫描状态。
6. 将上传结果固定为仅服务端可写的正式版本，计算并验证内容摘要、大小和必要安全检查。
7. 短事务发布文件版本、写审计与复制任务。返回当前可用状态，副本完成前显示复制中。

不能把客户端自报的 SHA-256 当作已验证事实，也不能把 Multipart ETag 当作跨供应商统一内容摘要。

### 4.2 分片与内存

候选默认分片为 32 MiB、并发 2，可根据网络和真机内存调节。120 GB 十进制文件约 3,577 个分片；120 GiB 则为 3,840 个分片，均需在实际供应商分片限制内验证。

Web 使用文件切片和有上限的读取，不一次加载整文件。Android 通过原生文件访问权限、流式读取与持久化任务模块上传，避免在 JavaScript 内存中复制巨大缓冲。前后台切换、系统终止与任务重启后可恢复；系统不允许持续后台传输时给出明确状态。

应用服务器不缓存整个 120 GB 文件，也不要求有 120 GB 空闲盘。计算摘要与跨云复制采用流式/范围读取，设置总缓冲和并发上限；完整校验可能需要读取整个对象，其时间和源端流量计入预算。

### 4.3 防止上传完成后的内容被替换

客户端只能写入本次上传的草稿位置，不拥有正式对象写权限。完成时用可验证的源版本/条件复制，或受控流式生成新的服务端对象，再对正式对象做校验与扫描。校验之后不得继续使用客户端仍可覆盖的草稿 Key 作为正式版本。

对于超过供应商单次复制上限的对象，采用分片复制或流式 Multipart；不能用一个简单 Copy 请求假设 120 GB 可完成。凭证不得授权完成后继续写其他 Key。

### 4.4 暂停、恢复、取消与清理

上传会话跨浏览器刷新/设备重启保存；浏览器重新选择本地文件后核对大小、文件指纹及必要片段摘要，再续传。后台以存储端分片结果为准，不能只信任本地进度条。

上传任务有效期、可恢复期与 Bucket 未完成分片生命周期保持一致。R2 默认会在 7 天后中止未完成分片，若业务需要更长窗口，需显式调整并计入存储费用。[R2 上传生命周期](https://developers.cloudflare.com/r2/objects/upload-objects/)

取消先阻止新分片，按策略中止 Multipart 并清理草稿；已正式发布的版本不能通过取消上传删除。失败上传和孤立草稿有周期清理，但清理任务必须排除仍在有效期内的上传和仍被业务引用的版本。

## 5. 小程序的文件能力

微信和抖音首发支持授权文件列表、版本/大小/状态、合同与票据等适配格式的预览、普通附件与审批。120 GB 文件显示元数据、业务关联和适用的访问入口，不要求小程序将整文件下载到本地。

普通附件大小先按 20 MB 测试目标验证，再按两端真实能力冻结。域名、文件选择/缓存、预览格式、前后台行为与失败提示逐端检查，不能从 Web 上传实现直接推导小程序表现。

大文件的媒体转码、整库解压或在线专业格式处理不属于文件存储本身；后续根据具体文件类型单独增加。

## 6. 跨云复制机制

```text
主版本正式发布
  → 数据库事务写 outbox
  → 领取复制任务
  → 固定源版本与摘要
  → 范围读取源数据 / 上传目标分片
  → 持久化每个已确认分片
  → 完成目标对象
  → 校验大小、摘要与目标可读性
  → 标记该版本 replica_verified
```

副本 Key 与版本 ID 对应；目标不存在时新建，已存在时先核对，不盲目覆盖。复制任务进度保存到 PostgreSQL，Worker 重启后恢复目标 Multipart；源文件新版本不改变本次正在复制的不可变源。

幂等键为“文件版本 + 目标提供商/桶”。网络中断、限流采用退避重试；凭据失效、策略拒绝等错误暂停并告警。大文件和小文件使用不同任务队列/权重，防止一个 120 GB 任务阻塞合同和票据的备份。

建议初期只允许一个大文件复制任务、两个分片并发，保留小文件通道。配置总出口带宽限额，避免复制影响 3 名员工的业务访问。提供待复制字节数、最老未完成版本、预计完成时间与失败原因；估时随吞吐变化更新。

源与目标使用实际内容摘要校验。若供应商返回的摘要算法或语义不同，不能直接比较 ETag；可在源读取时计算 SHA-256，目标进行完整回读验证，或使用经过证明的等价内容校验。全量回读会增加源/目标流量与完成时间，需明确计费路径。

每日核对元数据和复制清单；按周期进行内容抽检与恢复抽样。抽检不是全量已验证的替代品：首次导入与新版本标记双云验证前必须有可靠校验结果。

## 7. 传输时间与恢复指标

以下仅是 `字节数 × 8 / 有效比特率` 的理论下限，采用十进制单位，不含校验、API、重试和并发争用：

| 有效吞吐 | 120 GB 单向传输 | 2 TB 单向传输 |
| --- | --- | --- |
| 20 Mbps | 约 13.3 小时 | 约 222.2 小时 |
| 100 Mbps | 约 2.7 小时 | 约 44.4 小时 |
| 500 Mbps | 约 32 分钟 | 约 8.9 小时 |

若两次传输复用同一瓶颈，或需要完整目标回读校验，总耗时会增加。因此不能承诺 120 GB 在 15 分钟内完成跨云复制。

RPO 表示可丢失的数据时间窗口，RTO 表示恢复服务所需时间。候选目标必须经过现有服务器和实际链路演练：

| 数据/故障 | 候选目标 | 条件 |
| --- | --- | --- |
| 常用小文档跨云副本 | p95 在正式发布后 15 分钟内校验完成 | 暂限定单文件 ≤ 100 MB、网络正常、小文件保留队列；不是全文件 RPO 保证 |
| 120 GB 大文件跨云副本 | 按实际有效吞吐与校验路径逐文件估时 | 页面明确副本未完成；可配置归档须等待双云验证 |
| 已验证文件版本 | 双云副本保留完整字节和版本 ID | 依赖账号独立与保留策略；不包括仍在上传/复制的数据 |
| 托管 PG 同提供商故障恢复 | RPO ≤ 5 分钟、RTO ≤ 2 小时 | 以选定托管方案 PITR 与演练为准 |
| PG 提供商整体不可用的跨云恢复 | 初期 RPO ≤ 8 小时、RTO 4–8 小时 | 每 6 小时一致性逻辑备份并双云完成；备份时长与告警预算计入；大数据库需重估 |
| 应用节点丢失 | 重建应用与配置目标 ≤ 2 小时 | PG/文件/密钥可用，不要求先复制完全部 2 TB |
| 原生 Codex 线程丢失 | 恢复业务会话和提交记录，原生线程可能重建 | 已验证归档机制才承诺原生线程原样续接 |

故障发生前尚未完成跨云备份的最新文件可能无法从副本恢复。全系统可恢复时间点还受数据库与对象引用匹配限制，不能把每个数据域的最好指标拼成一个更强承诺。

## 8. 删除、历史与防误操作

用户删除先进入逻辑回收站，候选保留期 90 天；历史版本候选保留至少 180 天，合同签署件按公司业务要求另定。保留期是待确认策略，不是法规结论。

主端删除动作不立即硬删副本。后台 GC 同时检查业务引用、历史版本、备份恢复窗口、保留规则和显式清除授权。归档、回收和永久清除是不同动作。

R2 Bucket Lock 可阻止受保护对象被覆盖/删除，但管理员有修改规则的能力，不能据此宣称账户最高权限被盗时仍有绝对不可变保证。应用和复制凭据不授予修改保留规则的管理权限；管理凭据独立保存。[R2 Bucket Lock](https://developers.cloudflare.com/r2/buckets/bucket-locks/)

最少设置三类身份：应用主存储身份、复制身份、独立恢复/保留策略管理员。Agent 不获取这些密钥。确需抵御主账号被盗，可另设独立管理域和额外受限备份，计入成本与恢复流程。

## 9. PostgreSQL 备份

推荐独立托管 PostgreSQL，自带自动备份/PITR，并额外生成可移植加密逻辑备份复制到两个存储。逻辑备份至少覆盖业务、权限、文章版本、合同/费用、会话、审计、上传/复制任务、schema 与扩展版本信息。

初期候选：每 6 小时逻辑快照，并生成同一快照的文件引用清单；每日汇总备份目录。PITR 保留至少 14 天，逻辑备份按日/周/月分层保留。备份任务按真实数据库体积测试持续时间；失败告警不能只看最近一次启动成功。

如果需要跨云数据库 RPO 降到 15 分钟以内，必须另行验证基准备份 + 连续 WAL 归档，或适用的数据库复制方案。不是每个托管数据库都允许导出物理 WAL。`pg_dump` 逻辑文件不能当成 WAL 回放的物理基准备份。[PostgreSQL PITR](https://www.postgresql.org/docs/current/continuous-archiving.html)

备份文件以应用外密钥加密，密钥有独立恢复保管。恢复演练验证角色、权限、序列、schema、扩展和任务状态，不能仅以“备份文件存在”或文件大小正常判断可恢复。

## 10. 一致性恢复清单

每个备份目录关联数据库快照/恢复点、schema 版本、活动文件版本及对象摘要、副本验证状态、配置版本和恢复步骤。重要关系通过同一数据库快照导出，避免备份期间引用集合变化。

可恢复时间点 T 必须同时满足：数据库可恢复至 T，且 T 时正式引用的所有必要文件版本均存在于可用存储并经过校验。它由引用清单验证，不能用“最后一个文件复制成功时间”代替。

若最新数据库引用某个尚未复制的 120 GB 新版本，主云失效时可以选择较早完整恢复点，或恢复新数据库并明确标记该文件版本暂不可用。不能静默使用旧字节冒充该版本。恢复策略由业务选择，回执要列出缺失对象与任务。

## 11. 灾难恢复流程

1. 明确故障域，暂停有影响的写入；保存事故时间与当前存储 epoch。
2. 确认数据库、可用对象副本、恢复清单与密钥，选取经过验证的恢复点。
3. 先恢复账号、权限、项目和目录；对可用副本做授权读取，优先恢复业务访问。
4. 检查关键合同/费用、待审批、最新文件、会话和已提交工具结果。
5. 如需把副本提升为主写端，明确单一新主、写入代次、旧凭据限制和路由切换；防止旧节点重新上线继续写旧主。
6. 将事故期间待处理任务逐项对账，幂等重试，不盲目重播已提交审批、费用或通知。
7. 在后台重建另一份文件副本，恢复双云状态；记录实际 RPO/RTO 与改进项。

服务恢复不要求先把 2 TB 全部搬回原云；通过已验证副本读服务即可逐步恢复。完整重复制的完成时间另行记录。初期主副写入切换采用运行手册执行，不做未经验证的自动双主。

## 12. 2 TB 存量迁移

先盘点来源、总字节、文件数、类型分布、最大文件、所有者、路径编码、敏感分类、现有版本和已有摘要；文件类型目前未知，不假设都是办公文档。

迁移顺序为样本验证、建立项目/目录映射、分批导入主存储、记录摘要、复制副本、验证索引/权限、双份完整性核对、增量追平和切换。来源保持可读到正式验收，迁移工具不默认删除源。

迁移报告列出成功、失败、排除、重复候选、缺少归属和大小/摘要不匹配。2 TB 的首次跨云传输、完整校验与临时双份占用属于一次性费用，应单列采购。

## 13. 本地临时数据与访问保护

应用临时盘有按目录配额、24 小时失效候选策略和任务持有保护，实际清理不影响仍在运行的任务。上传/复制进度存数据库，不放在唯一的本地 checkpoint 中。备份临时文件加密并在验证双云完成后清理。

严格受限文件经实时鉴权代理访问；普通私有大文件可使用短时签名加 Range 下载和续签，避免整文件经过低带宽应用服务器。已签名 URL 在有效期内具有持有即访问的属性，敏感文件不把它发送到 TG 群。[R2 预签名安全边界](https://developers.cloudflare.com/r2/api/s3/presigned-urls/)

大文件权限回收、短时 URL 过期与长时间下载续传策略要一起验证。目录中的软删除不自动抹除已下载到员工设备的副本。
