归档须基于准确项目版本与完整核查依据，由当前有权人员在真实近期 MFA 下填写成果总结、经验复盘、后续跟进与原因，并分别明确确认业务与合同／财务／订阅处置。选取的可选附件固定正式版本。依据变化保留输入、重新读取后清空确认项，不能自动换用新依据。归档与复盘、审计及操作收据同事务；受控重开保留旧历史，再归档新增独立记录。Q-18 未决前不实现单项豁免。详细约束见[结项开发协议](../development/44-project-closeout-and-archive.md)与[页面设计](../design/17-project-closeout-and-archive.md)。

## 2. 任务与里程碑

任务字段：项目、标题/说明、负责人、参与人、优先级 low/normal/high/urgent、状态、planned_start/due_at、completed_at、parent_id、milestone_id、sort_order、版本。允许未分配任务但需在工作台提示；不把任务数直接等同项目完成百分比。

状态：`todo → in_progress → in_review → done`；`in_review → in_progress` 表示退回；未完成可置 `blocked` 并记录原因与此前状态；done 重开需理由；任意未完成可 cancelled。是否需要 review 为任务模板字段，无需验收任务可从 in_progress→done，后端判断。

PM-06：首发只支持同项目 finish-to-start 依赖，新增/修改时事务内检查环（含并发新增），不得依赖前端检查。前置未完成时禁止进入执行或完成；例外权限按 Q-18 冻结后才能开放。父子任务不能成环；父任务完成需所有未取消子任务完成，删除/取消不悄悄删除后代。

PM-07：里程碑含目标日期、负责人、关联任务/交付、状态 open/achieved/missed/cancelled；按任务和交付实际验收决定 achieved，过期未达成显示 overdue/missed 信号。进度与超期是派生事实，不能由模型手填“100%”替代证据。

## 3. 交付、风险、问题与变更

| 对象 | 状态/字段 | 关键规则 |
| --- | --- | --- |
| 交付 deliverable | draft → submitted → accepted / changes_requested；重提新修订 | 提交固定 file_version_ids、验收准则、提交人；验收决定固定修订与验收人 |
| 风险 risk | open → mitigating → closed / realized | 记录概率/影响/对策/owner；realized 创建关联问题而非抹掉风险 |
| 问题 issue | open → investigating → resolved → closed，可 reopen | 严重度、负责人、期限、证据；关闭需解决说明 |
| 范围变更 change | draft → in_review → approved / rejected / withdrawn → implemented | 保存范围/预算/时间影响；批准不等于自动修改项目，实施时校验项目版本 |
| 预算 budget | 多个修订，draft/approved/superseded | 按币种/类别/周期；增加预算需批准修订，不覆盖旧预算 |

PM-08：验收只改变对应交付修订，不因任务 done 自动 accepted。新文件版本不会悄悄替换已验收文件，需新交付修订。项目成本来自实际费用分摊，预算和预测单列。

PM-11（范围变更与预算的首发细化设计）：提案保存完整拟实施范围、日期、影响说明、准确正式文件版本，以及当时的项目和该币种预算基线。审批通过仅形成批准依据；有权人员还须核对准确修订、近期MFA及范围／预算影响后明确实施。基线或批准依据已变化时拒绝旧操作；实施不自动修改任务日期，不生成实际费用或收付款。

预算按币种、类别及含首尾的日期期间管理；同类别期间不重叠，币种之间不直接合计。同一变更的币种固定。预算不变与明确清空必须区分，完整替换保留旧预算。审批金额采用各类别／期间的正向增加合计，减少不得抵消其他项增加；预算净变化、建议预算总额、实际费用分别表达。已实施预算与固定提案、审批、实施历史均可追溯，预算及变更读取须有明确预算权限。

活动或暂停项目的范围／日期不得通过普通编辑绕过变更流程；草稿可完善基础资料。多份提案基于同一项目时，实施第一份后须重新核对其他提案的项目版本。归档、取消及结项核查中的项目保持只读。具体接口、事务和未完成客户端范围见[变更与预算实施协议](../development/43-project-changes-and-budget-revisions.md)。

PM-09：评论含作者、时间、编辑历史、附件版本；通知 @ 仅限有权成员，转发/引用不扩大权限。首发不需在线共同编辑或全量聊天替代任务记录。

## 4. 项目博客与知识

PM-10：支持 project_log、meeting_note、sop、article 类型，标题、摘要、Markdown/受限富文本、项目可选、标签、分类、作者、正文修订、附件。正文/历史在 PG，不以临时工作区为唯一记录。

状态 `draft → published → archived`；退回 draft 产生可追踪动作；published 指内部发布。编辑先生成草稿修订，发布时检查 base_revision；已发布版本保留，恢复历史生成新修订。未发布草稿只作者和获授权编辑者可见。

附件可以“跟随当前版”或“固定 file_version_id”，界面必须标出；会议结论、合同和验收建议固定版本。文章权限不得掩盖附件权限；无权附件不显示敏感标题，文章内已存在的敏感正文需按文章本身分类控制。

知识检索按标题/标签/正文/项目过滤，支持中文与英文测试集；秘书摘要附来源版本、时间和待确认项。SOP 不是可执行 Skill，上传一份同名 Markdown 不得改变秘书工具权限。

2026-10-25 秘书知识写入增量：按准确项目／分类／原修订生成草稿与单独核对后内部发布，复用本章知识权限、修订和发布指针。所有模型观察来源不得超出目标项目及分类。完整边界和证据见[增量58](../development/58-secretary-knowledge-writes.md)。

2026-10-25 秘书项目更新增量：已有里程碑可按准确版本修改标题、实际项目成员负责人及带时区日期，或执行原状态机；达成须满足原关联任务／交付条件。项目阶段沿用范围、成员、结项阻塞及重开权限，归档仍由人工结项复盘。一个运行只授权一个准确对象／动作，新建及关联编辑未纳入秘书工具，见[增量59](../development/59-secretary-project-stages.md)。

## 5. 场景验收

移动项目资料、讨论与固定交付修订按[移动项目协议](../development/45-mobile-project-collaboration.md)实施，交付继承同一准确修订与人工验收规则。该公共页面增量不会减免项目创建／配置、变更／预算／结项、文件内容、两小程序及Android真机的原有要求。

完整样例：创建项目 → 建两项有依赖任务 → 添加预算/合同 → 上传两个交付版本 → 首次验收退回 → 修订再验收 → 记录风险转问题并关闭 → 关联一次实际费用 → 归档与复盘。验证所有链接可追踪、归档禁止普通写入，费用不因多处关联重复统计。

异常样例：并发加反向依赖、旧版本变更实施、无权成员分配、无证据验收、遗留费用试图归档、文章引用失权文件均应得到确定拒绝或明确阻塞清单。
## 秘书里程碑创建与任务关联的实现补充（增量72）

项目会话允许员工完整指定里程碑标题、有效成员负责人、含时区的目标时刻与原因，固定当前项目版本后发送。选择和预览不执行创建；普通聊天不能补足或替代准确授权。新 ID 由原业务分配，结果版本从 1 开始，与父项目基础版本分别呈现。项目阶段、负责人资格、当前权限、全体受众、原登录、取消及版本冲突规则继续生效。

创建里程碑不会自动关联任务。员工通过另一份准确任务更新选择同项目开放里程碑，明确解除时发送空关联；跨项目或已关闭里程碑由原任务命令拒绝。任务更新入口及候选分页在 Web／Taro 共用事实与版本约束，不替代任务验收或交付流程。实现与本地验收范围见[增量72](../development/72-secretary-milestone-creation-and-task-association.md)。

## 秘书交付资料与关联的实现补充（增量73）

项目会话允许员工选择实际交付，并完整核对名称、验收准则、有效项目成员负责人以及同项目里程碑关联。请求固定交付自身版本和原因；四项资料必须同时存在，保持原值也须核对。解除关联须明确发送 `null`，缺项不得代替清空。普通聊天、选择、预览和历史回执均不产生写授权。

准确工具复用原交付资料更新命令，仅允许协议1的草稿或退回记录。原关联已关闭时须按原业务重开，跨项目、关闭里程碑或无效负责人不得绕过。更新不改变交付状态、正式修订、固定文件和验收决定；员工仍通过原交付页面提交、退回、再次提交和验收。原登录、当前权限、共同受众、项目阶段、准确版本和取消继续逐次检查。详细约束及真实回归见[增量73](../development/73-secretary-deliverable-updates.md)。

## 秘书创建交付草稿的实现补充（增量74）

员工可在项目会话固定父项目当前版本、交付名称、验收准则、实际成员负责人、同项目里程碑或明确不关联及原因，发送完整创建授权。Web／Taro提供空白表单与完整预览；预览不写业务数据，缺项或普通聊天不允许秘书补足。创建沿用原交付权限、项目阶段、成员、关联、共同受众和原登录规则。

原业务分配真实新交付 ID，创建协议1草稿；结果版本1和空正式修订与父项目版本分别核对。重试复用原操作和新 ID，不重复创建。正式文件、提交及验收继续由员工在原交付页面办理，后续资料更改须另发准确新交付授权。实现、原里程碑空白字符修正及本地验证见[增量74](../development/74-secretary-deliverable-creation.md)。

## 移动立项、资料及成员操作的实现补充（增量75）

移动项目列表可新建立项，当前本人为负责人，可选准确已发布模板并核对系列、修订与完整结构；真实回执展示新项目及初始化结果。项目详情可编辑资料：草稿可明确清空日期，进行中／暂停项目的范围及日期继续经原项目变更审批，普通更新不发送这些字段。

成员页可选择实际有效用户配置成员／管理员／只读角色或明确移除，负责人移交为独立命令；两者固定项目版本，均不替代业务角色授权。本人／owner限制、未闭环事项阻止移除、只读阶段及撤权沿用原业务。冲突或响应未知保留输入并阻止再次提交，先重新读取真实结果。实现及7条真实流程见[增量75](../development/75-mobile-project-setup-and-members.md)，四端正式验收仍按原范围执行。

## 移动里程碑、风险与问题的实现补充（增量76）

移动项目各事项列表可新建里程碑、风险和问题，详情可按当前阶段编辑资料或明确跟进状态。负责人必须是实际有效项目成员，目标／截止时间按香港时间核对，并保留原业务微秒精度；编辑使用事项自身版本，不隐含状态变更。里程碑达成仍须满足实际任务／交付完成证据。风险应对、关闭、重开和问题调查、解决、关闭、重开沿用原状态规则；解决／关闭问题必须填写实际解决说明。

风险发生使用原事务生成唯一关联问题，结果未知时先读取风险和实际问题，不自动再次提交；原风险之后只读。概率未设置也须显示应对措施和真实问题链接。既有期限／概率暂不能清空的原接口边界必须明确呈现，不得把服务端保留原值显示为清空成功。viewer、只读项目、撤权、版本冲突和错误项目深链接继续限制写操作。实现及验证见[增量76](../development/76-mobile-project-milestones-risks-and-issues.md)。
