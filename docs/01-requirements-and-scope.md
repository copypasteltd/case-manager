# 需求、范围与使用场景

日期：2026-10-22。版本：v0.2。标记约定：U 为用户已提出；D 为设计建议；A 为估算假设；Q 为待确认。

2026-10-23同步R-08首发Skill清单；完整细化与正式枚举见 [文档中心](README.md) 中的v1.0-draft基线。本篇保留原U/R编号及立项上下文。

## 1. 目标与成功标准

建设公司统一内部工作平台，让员工围绕项目查找资料、更新进度、办理申请、查看服务状态，并通过秘书完成可追踪的日常操作。

业务成功应通过试点前后的数据验证：找资料耗时、项目资料完整率、重复录入次数、申请周转时间、秘书任务成功率、错误更新次数、故障发现时延和备份恢复成功率。首期先测量基线，再确定改善幅度，避免以“接入 AI”作为唯一成功标准。

### 5.1 合同管理首发闭环

合同台账包含编号、类型、相对方、关联项目、负责人、金额/币种、起止时间、付款/收款节点、到期与续约提醒、审批状态和签署件版本。状态建议为草稿、审核中、已批准、待签署、履行中、已完成/已终止；退回保留历史。

支持主合同、补充协议关联，变更保留版本与审批记录；签署件和工作草稿分开标记。履约节点关联任务、采购/报销和费用记录。合同审核由有权人员负责，秘书可提取字段和提醒，不将模型理解当作法律结论。电子签名服务不默认包含在首发范围。

### 5.2 报销管理首发闭环

报销单包含经办人、发生日期、项目/公司费用、类别、明细、金额/币种、票据和说明。流程为草稿、提交、审核、退回/通过、待处理、已处理；财务处理与审批通过分别记录。首发支持人工登记实际支付日期、金额与凭证。

票据按摘要、供应方、日期与金额提示重复候选，最终由经办/审批人核验。票据 OCR 可辅助录入但保留原件与修改痕迹；需要识别的格式/语言由样本验证。关联采购或订阅的支出共用实际费用记录，不能重复计入月开支。

### 5.3 采购管理首发闭环

采购从需求申请开始，记录用途、关联项目、预算、供应商/报价附件、审批、订单记录、交付/验收、付款处理记录和关闭状态。支持部分验收和分次支付记录，实际是否需要多轮比价由业务确认。

3 人组织允许配置经办人与审批关系，是否允许本人审批必须由公司规则明确。不要硬编码多部门流程，也不能默认所有三人都能互相批准所有金额。

### 5.4 月度开支与订阅管理首发闭环

订阅台账包含供应商、产品/套餐、负责人、关联项目/公司费用、周期、币种、预计金额、下次扣款日、续费/取消状态和安全的付款方式标识。系统不保存银行卡完整卡号或安全码。

按账期生成预计开支，人工或经核准接口登记实际扣款、票据和异常。支持月付/年付等周期、价格变更生效日期、续费提醒、取消与历史记录。月报区分预计、已发生、已处理，按项目/类别/供应商汇总。

如同时需要“实际现金支出”和“按月摊销成本”，应分开显示；年费不能同时按全额支付和每月摊销重复计入同一个口径。多币种保留原币，汇总时使用经公司确认的记账币种、汇率来源与记账日期。

### 5.5 完整项目管理首发闭环

本规划将“完整”具体化为：项目立项与范围、负责人/成员、任务与子任务、优先级/期限、任务依赖、里程碑、文件/日志、合同关联、项目预算与实际成本、风险与问题、范围变更、交付清单、验收记录、归档与复盘。

项目详情提供列表/看板及基础时间线。完成任务不自动意味着交付验收通过；关闭项目需检查未完成任务、交付文件、验收结论及未处理合同/费用。复杂资源优化排程与自动工时不属于当前“完整”的默认含义。

## 6. 信息架构

管理门户建议包含：

1. 工作台：个人待办、审批、近期项目、需要处理的异常。
2. 项目：列表、项目概况、成员、任务、文件、日志、关联服务、归档。
3. 文件与知识：跨项目授权搜索、公司公共资料、版本与回收站。
4. OA：发起申请、我的申请、待我处理、已处理、模板配置。
5. 秘书：新会话、会话列表、执行计划、进度、待处理操作、结果与来源。
6. 服务状态：服务列表、事件、维护、最近探测和状态变更。
7. 管理设置：组织、权限、AI 技能发布、存储复制、费用、审计。

项目是聚合入口；文件、日志和服务保留稳定 ID，可在授权后跨项目关联。所有移动端入口沿用这些业务对象，避免分别维护一套资料。

## 7. 核心业务场景

### 场景 A：新项目建立

员工提供项目名、业务类型、负责人、预计周期和成员。系统检查必填字段、项目编号与重名风险；按模板建立项目、逻辑目录和里程碑；最后给出项目链接和已完成清单。可以手动表单发起，也可以由秘书发起，最终走同一个业务流程。

创建的项目、目录、成员关系应在数据库事务中完成。后续异步生成模板文件若失败，显示待补齐并允许重试，不能把不完整结果报告为全部完成。

### 场景 B：文件更新

员工选择文件或向秘书说明改动。系统读取当前版本并生成新版本草稿；文本可显示差异，二进制文件展示新版本与预览。提交前核对基础版本，处理并发修改；成功后记录作者、执行人和来源。

“任何格式均可纳管和替换”与“秘书能理解并精确编辑任何格式”分开验收。首期重点支持 Markdown、文本及已验证结构化格式；PDF、Office、图片等按解析/生成适配器逐步开放。

### 场景 C：资料检索与总结

员工问“某项目最近进展和最新交付文件”。系统只检索该员工可见的项目、日志和文件版本，摘要附可点击来源与时间。如果资料不足或版本陈旧，明确说明缺失；不能把推断状态当作已批准的项目状态。

### 场景 D：OA 申请与审批

员工填写合同、报销或采购表单，或由秘书整理草稿，提交后进入对应审批链。审批人可以同意、退回或按制度撤回；任何审批结果都记录当时模板、审批人和内容版本。秘书可整理材料和提醒，具体审批身份与权限由系统验证。

首期只实现已确认的流程规则。涉及报销付款等场景时，先定义“申请/审核/已处理”的记录边界，是否连接支付执行应独立提出需求。

### 场景 E：股东群询问

已绑定股东在指定 TG 群提及 Bot 查询项目摘要。Bot 根据该用户权限和群可公开范围取数，先确认范围，再返回摘要及需要登录的门户链接。个别股东可见而群范围不可见的内容，转到个人授权入口处理。

### 场景 F：服务异常

外部探测发现服务异常，更新状态、触发去重告警、关联项目与负责人。秘书可汇总现象和已授权的指标；修复操作形成待办或经授权的运行手册任务。首期以只读分析和人工处理为主。

| 项目 | 候选验收目标 | 说明 |
| --- | --- | --- |
| 普通业务接口 | 3 人基线及 10 人余量场景下 p95 ≤ 500 ms | 服务端计时；排除大文件传输、复杂搜索与模型推理 |
| 大文件上传 | Web/Android 支持 120 GB 分片续传，文件摘要一致 | 模拟断网、应用重启、凭证过期；不设脱离带宽条件的完成时间 |

| 搜索 | 基线测试集 p95 ≤ 2 s | 明确测试数据量、中文内容与 ACL；不含长文生成 |
| 会话接收 | 服务器收到后 2 s 内返回任务 ID/排队状态 | 模型首字与最终完成时间另记录，不承诺固定推理时延 |
| Web 恢复连接 | 按事件序号补发进度，不重复执行业务写入 | 需要事件持久化和幂等 |
| 状态更新 | 60 s 探测、连续失败确认；过期显示 unknown | 具体探测周期按业务和告警成本设置 |
| 数据安全 | 未授权访问、跨项目检索泄露和越权写入验收零通过 | 属于必须满足的功能正确性标准 |
| 可用性 | 单节点试点先量测；生产候选目标 99.5% 月可用性 | 需明确维护窗口；约 3.6 小时/月故障预算，并非现有 SLA |
| 可恢复性 | 按数据域设置 RPO/RTO 并演练 | 详见存储设计；跨云数据库不能沿用同云 PITR 指标 |
