# 申请快照与顺序审批

承接 [审批协议](21-oa-approval-and-business-revisions.md)。迁移 `0028_approval_instances.sql` 与 `internal/workflow` 实现本章事实。当前接入业务为合同；采购、报销与项目变更仍待各自业务模块，不能把通用 kind 枚举当作已经接入。公司审批人、金额区间和本人审批政策由业务明确发布，开发环境不自动预置制度。

## 1. 数据与状态

| 对象 | 固定内容与边界 |
| --- | --- |
| requests | 申请人、业务归属、项目/分类、当前修订及当前实例；头版本随状态推进递增 |
| request_revisions | 准确业务修订、业务摘要、完整结构化内容、正文版本、制度快照及指定人的授权依据；只追加 |
| approval_instances | 一次送审的准确申请修订与制度修订；重提生成新实例 |
| approval_steps | 固定顺序、职责、指定人及送审时姓名、MFA要求与权限依据；同一实例最多一个 active |
| approval_decisions | 唯一步骤决定、准确申请修订及摘要、实际人工会话、身份验证时间、权限证据与原因；只追加 |
| approval_withdrawals | 一次实例的撤回依据与操作者；只追加 |

申请状态为 draft/in_review/approved/returned/rejected/withdrawn。仅草稿、退回和已撤回申请可刷新内容、再次送审；拒绝为该申请终态，需从合同建立新申请。旧申请、决定和文件引用继续保留。已批准也不能通过撤回接口改写。

合同审批线与申请状态在数据库延迟约束中保持一致；draft 对应 not_submitted。最后一步批准仅使合同进入 pending_signature，并固定 approved_revision_id，active_revision_id 仍为空。它不登记签署、生效、费用或付款。

步骤必须与准确已发布制度一一匹配，不能追加未计划审批人。延迟约束检查完整步骤集合、active 数量及终态；触发器阻断提前激活后续步骤、改写固定身份/证据、终态回退与审批快照原位更新。文件在申请修订事务中登记 approval_snapshot 引用，不自动释放旧修订保护。

## 2. 草稿、预览与送审

合同详情的“准备送审申请”先创建固定申请草稿。缺少金额、往来方或正文仍可准备；送审前必须补齐收付方向、类型、类别、往来方、负责人、币种金额、起止日期与正式正文版本。

普通合同编辑只修改合同修订，并令相关可编辑申请回到 draft；不会自动把新合同内容替换进旧申请快照。申请人通过“更新申请草稿”明确核对当前完整合同，再保存新申请修订。基础版本、业务修订和业务摘要均需准确匹配。

送审预览读取当前唯一匹配的启用制度，重新检查完整业务、正式文件的扫描/例外证据、往来资料及每位审批人的权限。预览摘要绑定申请版本、申请修订、提交内容、制度修订、授权依据、操作者及组织授权版本和渠道。正式送审重新计算并比对；制度或权限改变使旧预览失效，不自动采用新流程提交。

送审事务依次锁定组织授权、实际用户、项目、业务与申请；同一事务追加固定快照、实例与全部步骤，激活第一步，更新申请/合同状态并写审计、Outbox、幂等结果。云、模型和通知调用均不进入此事务。失败不得留下孤立实例或部分步骤。

## 3. 权限与人工决定

request_manager、approval_reviewer 和 contract_reader 是独立、默认不绑定的角色。对象读取同时要求申请及原业务权限；往来方、正文引用各自重新授权，失权时隐藏名称和内容。配置管理员不自动获得申请阅读权。

送审检查每位指定用户处于 active，并实际拥有申请读取、审批决定、合同读取、往来资料读取和附件读取权限。授权检查使用真实范围、分类、渠道及显式资源授权；不会因被分配审批而自动授予正文读取权。证据固定当前用户/组织授权版本、匹配绑定及资源授权标识、分类政策版本和检查渠道；这些内部标识不进入普通业务响应。

决定只能来自指定人的 Web、Android、微信或抖音人工会话。服务从数据库核对实际会话、设备、授权版本及所需的近期 MFA；不能信任调用者伪造的身份验证时间。Agent 不能审批，其他人的有效会话也不能替代本人。

每次决定重查当前权限和准确申请修订、摘要、步骤/申请版本。批准只推进下一步；最后一步才批准申请。退回、拒绝、按制度撤回均取消尚未执行步骤，保留已发生决定。本人审批默认阻断，必须由所选制度明确允许；停用审批人、文件失权或失效扫描依据均明确阻断，不自动换人或跳步。

同一步骤有唯一最终决定。并发决定最多一个成功；幂等重放先鉴权，返回历史结果不再次推进。旧实例的撤回重放不能取消新实例；返回内容重新检查当前关联资料权限。审计失败使本次业务状态、引用、步骤与幂等结果全部回滚。

## 4. 接口与客户端

| 路径 | 方法与能力 |
| --- | --- |
| /v1/requests | GET 权限过滤后分页；POST 从准确业务基础版建立申请草稿 |
| /v1/requests/{id} | GET 当前固定内容、步骤及对象能力 |
| /v1/requests/{id}/revisions | GET 历史分页；POST 明确刷新为新的草稿修订 |
| /v1/requests/{id}/revisions/{revision} | GET 准确申请修订及该次步骤 |
| /v1/requests/{id}/submission-preview | GET 本人当前会话下的完整送审预览 |
| /v1/requests/{id}/submit | POST 准确预览摘要与制度修订送审 |
| /v1/requests/{id}/withdraw | POST 本人按固定制度撤回当前实例 |
| /v1/approval-tasks | GET 当前分配给本人、满足读取权限的 active 步骤 |
| /v1/approval-steps/{id}/decisions | POST 准确步骤/申请版本、修订与摘要的人工决定 |

精确 DTO 由同源 OpenAPI 生成；未接入的业务类型明确拒绝。列表先过滤权限和实际分配再分页；游标绑定当前身份、授权版本、渠道及筛选，不能跨账号复用。

Web 新增 /requests、/requests/:id、/approvals。合同入口由服务端 can_prepare_request 控制；刷新、送审、撤回及处理步骤也使用实际对象能力。预览不会因窗口聚焦自动换成新制度，重新读取须明确操作；原因保留，失败后确认禁用。MFA 在原决定表单中进行，验证本身不提交决定。历史只读展示各次内容与顺序。

沿用 [组件约束](../design/03-components-and-patterns.md) 的品牌令牌、语义状态和模态框。业务阶段与审批状态分别表达，未知值不显示为零。小屏内部滚动，长原因折行，确认文案写明主体与动作。页面按路由分块加载，UploadProvider 保留跨路由传输状态；加载失败给出明确重载入口。

## 5. 验证与限制

17 个隔离原生 PostgreSQL 叶场景覆盖准确送审、两名人工审批人、并发、退回重提、拒绝后新申请、撤回重放、本人审批、失权/停用、真实会话 MFA、游标与证据不可变、四种审计失败回滚、制度变化与数据库边界。正式文件由受控测试提供商生成，不能作为真实 OSS/R2 或 120GB 的证据。

[浏览器记录](../quality/evidence/requests/result.json) 有 6 条真实 API/UI 检查链：草稿、缺项阻断与原因保留、真实并发冲突、明确刷新与双份历史、双主题五宽度/待办空态、配置管理员及无关员工隔离。全部使用虚构合同，三项临时项目授权已撤销，浏览器全部关闭。390px 浅色预览阻断和 1440px 深色详情截图已人工复核。

上述开发库检查没有真实云正文，保留草稿与阻断分支的证据边界。后续[受控浏览器正向链](../quality/evidence/business-execution/result.json)使用独立原生数据库、受控正式文件和真实 Web 登录/MFA，已验证完整送审、独立人工批准及签署生效页面；仍不属于真实 OSS/R2 或120GB证据。签署与生效已由[签署实施](25-contract-signature-and-activation.md)接入；采购/报销/项目变更适配、合同履约、费用/付款、实际通知及移动客户端继续实现与验收。
