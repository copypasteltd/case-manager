# 秘书项目创建计划与准确批准

本阶段把秘书的项目创建请求连接到真实项目服务。先固定计划，员工核对并批准，再提交项目；计划回复与项目已经创建是两个独立事实。代码位于 `app/backend/internal/agent/plan*.go`、`app/backend/internal/httpapi/agent_plans.go`、`app/web/src/ConversationPlans.tsx` 和 `app/mobile/src/pages/secretary/plans.tsx`。

## 1. 实施范围

| 项目 | 当前实现 |
| --- | --- |
| 动作 | 一份计划只执行一次 `project.create` |
| 会话 | 发起人自己的公司私密会话；不接受项目共享会话或 TG 群授权 |
| 资料分类 | 公司内部、项目受限；不通过此入口创建严格受限项目 |
| 人员与模板 | 负责人、最多30名额外成员、可选已发布模板；复用项目人员校验与初始化 |
| 用户入口 | Web、Taro公共页面：拟定、查阅、批准、撤销、创建、打开结果项目 |
| 秘书入口 | `project-create` 的 MCP `propose_project`、`create_project`；无模型批准工具 |
| 角色 | 新增 `agent_plan_operator`，不自动绑定员工；项目创建、成员管理、会话及运行权限仍分别检查 |
| 发布 | 本地功能和受控执行测试；八项实际 Skill 仍为 draft，不因本功能落地自动启用真实模型 |

这是固定单动作批准的首条业务实现。长期预授权、批量条目、文件或 OA 写入、共享会话批准及 Skill 发布管理仍按原目标推进，不由本阶段替代。

本地使用入口为“公司秘书 → 本人公司私密会话 → 项目创建计划”。管理员通过既有人员／角色管理为指定员工绑定 `agent_plan_operator`；员工同时需要会话／运行和项目创建权限。项目私密会话与共享会话不显示此计划入口。没有活动运行配置时仍可人工拟定并核对计划流程；“由秘书拟定”另依赖已发布技能、配置及通过原生隔离验证的实际执行器，不能用人工入口代替真实模型验收。

## 2. 固定内容和状态

`0049_agent_project_plans.sql` 新增 `agent_plans`、`agent_plan_events`。固定意图绑定计划 ID、发起人及授权版本、会话准确修订和安全版本、可选来源任务、完整项目参数、模板修订与结构摘要、原因、创建时间及到期时间。采用规范 JSON 的 SHA-256；数据库核对原规范文本摘要及其与执行字段的一致性。意图字段不能更新，事件不能改写或删除。

有效期为数据库时间起30分钟。模板绑定 `revision` 及其结构内容摘要，防止同一模板 ID 在批准后被替换。

批准卡片展示固定项目类型、范围、负责人、额外成员准确 ID、独立的开始／截止日期及模板标识、修订和摘要；未指定模板时说明标准目录初始化。有效期展示香港日期和时刻。Web／移动手动拟定表单先覆盖本人负责的基础项目；其他人员、模板等参数须从准确计划中核对，不能仅凭标题或摘要批准未见参数。

| 当前状态／版本 | 可接受动作 | 结果 |
| --- | --- | --- |
| proposed / 1 | 本人批准 | approved / 2；保留准确计划摘要、实际会话及 MFA 证明 |
| proposed / 1 | 本人撤销 | revoked / 2 |
| approved / 2 | 本人撤销 | revoked / 3 |
| approved / 2 | 提交准确计划 | committed / 3；保存业务 operation ID 和 project ID |
| committed / 3 | 核对原批准版本的提交结果 | 返回同一项目和业务回执；不再创建项目 |

批准和人工提交要求有效员工会话、对应渠道以及最近10分钟内的真实数据库 MFA 记录。移动页面可复用仍有效的近期验证，不要求在同一次批准与创建之间重复输入动态码。后台仍独立核验。撤销无需重新批准，过期或失效的未提交计划也可以撤销。

批准不是永久授权。提交时再次核对当前权限、会话修订、安全版本、人员状态、模板快照与有效期；来源任务取消、失败、中断或尚未完成且超时，也会阻止其计划继续执行。先前任务已诚实返回 pending 时，可以在后续任务消费同一人员、同一会话的准确批准。

## 3. 接口与幂等

| 方法 | 路径 | 请求／结果 |
| --- | --- | --- |
| GET | `/v1/conversations/{id}/plans` | 当前本人可读的最近50项、`has_more`、阻塞原因及可操作标记 |
| POST | `/v1/conversations/{id}/plans` | `AgentProjectPlanCreate` → 201 `AgentPlan`；仅拟定，不创建项目 |
| GET | `/v1/plans/{id}` | 当前权限下的计划及实际业务回执 |
| POST | `/v1/plans/{id}/approve` | `AgentPlanAction` → 200；准确版本、计划摘要、原因 |
| POST | `/v1/plans/{id}/revoke` | 同上；撤销未提交计划 |
| POST | `/v1/plans/{id}/commit` | 同上 → 200；短事务内完成创建，非异步202 |

所有 HTTP 写入继续要求 CSRF／设备会话规则和 `Idempotency-Key`。旧请求重放前仍检查当前访问权限；响应投影重新查阅当前计划，避免展示已经撤销或已提交计划的旧按钮。

项目业务幂等键固定为 `agent-plan:{plan_id}`，内部路由固定为 `/internal/agent-plans/project.create`。另一个提交请求标识也只核对同一批准的结果。重新拟定不同参数必须产生新计划并重新批准。

## 4. 原子执行与权限边界

`platform.Commands` 增加可选 `Tx`。只有受控的业务协调代码传入已有事务；每次嵌套命令仍执行授权、幂等、审计及 outbox，外层负责整个事务的提交与错误回滚。普通业务调用保持原来的独立事务行为。

批准计划通过 `project.Service.Create` 创建项目，不维护另一套项目插入逻辑。项目、根目录与默认子目录、模板任务和里程碑、项目操作记录、计划状态及不可变回执在同一事务提交。短时组织锁与业务授权变更互斥；事务内不调用模型或外部网络。初期3人使用此保守锁策略。

数据库约束要求计划事件连续、状态与事件一致，批准附带有效 MFA 会话，提交附带本计划准确内部路由、幂等键、人员和真实成功项目操作。回执写入失败必须回滚项目及其所有关联记录。

## 5. MCP、结果与历史查阅

`project-create` 运行配置的准确工具集合为 `read_resource`、`search_resources`、`inspect_operation`、`propose_project`、`create_project`。原生执行证明必须匹配这5项；不能沿用只读3项工具的证明。`inspect_operation` 可接受准确 `plan_id` 核对本人计划，不能批准或变更计划。

MCP 的 `propose_project` 只接受项目参数和原因，会话版本、安全版本及身份从已绑定的执行任务取得；模型传入安全版本字段会被拒绝。负责人省略时拟定为发起人本人，完整计划仍须本人核对并批准。当前 MCP 没有人员或模板目录查询工具，不能要求模型猜测其他人员或模板 ID；人工 HTTP 拟定接口仍要求明确版本和负责人。

`propose_project` 返回 pending 和准确计划引用；无业务 operation ID、`committed=false`。`create_project` 只消费既有人工批准，返回真实资源与 operation ID、`committed=true`。工具账本、Node验证和 Go 最终提交均核验凭证，模型不能凭文字、随机 operation ID 或拟定成功声称项目已完成。

本阶段最初的跨轮测试显式提供准确 `plan_id`。后续[计划查询与明确引用增量](49-secretary-plan-discovery.md)已加入本人当前会话的有界计划查询、固定意图读取及Web／Taro明确引用入口；多候选仍须明确选择，不能把自然语言“执行刚才那份”直接当作准确授权。以下本阶段验证记录保留原来的来源与执行范围，新增量另有独立证据。

新增内部来源类型 `agent_plan`，代表不可变计划意图，不是跨项目的通用资料读取入口。它限定本人私密会话；关联项目创建后，后续工具和历史回复还要检查当前项目及 AI 阅读权限。不能通过计划回执继续披露已撤权项目。回复中的计划引用使用固定意图摘要，批准状态变化本身不会被误判为意图改变。

## 6. 验证与继续实施

原生 PostgreSQL 测试 `TestAgentPlans` 覆盖准确批准、近期 MFA、参数／人员身份替换、撤销、会话和模板变更、过期、事务失败回滚、安全重试、并发单次创建及数据库不可变约束。`TestAgentProjectTools` 通过实际本地 MCP／控制协议验证5项工具证明、跨轮次人工批准、真实业务结果、伪造完成拒绝、来源任务取消与历史撤权。

构建、操作证据和运行限制统一见 [本阶段证据](../quality/evidence/secretary-plans/verification.md)。Web 和 Taro H5 的真实页面操作不等于微信／抖音真机或 Android 原生执行验收。

后续继续扩展项目更新、文件有限读取与新版本提交、目录整理、知识与 OA 草稿、订阅／状态汇总；同时补充预授权规则和 Skill 发布生命周期。真实服务器原生隔离启动器与签名证明、模型服务、TG、Android宿主、120 GB／2 TB及双云恢复仍需各自交付和验收。
