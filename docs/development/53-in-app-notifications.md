# 站内通知、当前职责与投递记录

本增量推进 [GAP-08](../delivery/03-goal-gap-assessment.md) 和 [OPS-04／PG-19](../requirements/08-status-notifications-and-nfr.md)。员工可以在 Web、微信／抖音共用的 Taro 页面查看业务通知、区分未读与仍需处理、打开对应资料；运行人员可以核对投递异常。代码位于 `app/`，本说明和验证记录位于 `docs/`。

## 1. 本次实现

| 编号 | 能力 | 实现约束 |
| --- | --- | --- |
| NTF-01 | 实际事件消费 | 消费已经提交的业务 Outbox；通知失败独立重试，不能回滚原业务 |

Taro 新增通知中心和订阅账期查阅页，公共页面总数由 11 增至 13。账期页展示当前实际状态、起止日期、时区和预计／实际金额；后续费用关联、差异复核仍使用 Web 对应业务入口。

## 2. 事件与接收范围

| 类别 | 实际来源 | 接收范围及当前职责 |
| --- | --- | --- |
| 任务 | `task.created`、`task.updated`、`task.transitioned`、`task.dependencies.changed` | 当前未完成、未取消任务的负责人；改派后原负责人不再看见该通知 |
| 待审批 | `request.submitted`、`approval.step.decided` | 当前有效审批实例中处于 active 的步骤负责人；步骤变化后“仍需处理”随实际 `can_decide` 更新 |
| 申请进展 | `approval.step.decided` | 申请人；批准／拒绝作为进展，退回仍需处理；不等于合同生效或登记付款 |
| 合同到期 | `contract.reminder.due` | 现行有效修订的负责人，未指定时使用创建人；准确固定生效修订、截止日和本次提前量 |
| 订阅账期 | `subscription.reminder.due` | 已持久化提醒中、仍与现行账期责任人一致的员工；仅向有效 forecast 账期投递 |
| 文件副本 | `replica.failed` | 正式版本作者和文件创建人，合并同一接收人；必须具备文件及当前目录访问权；恢复后实时显示 verified，停止提示待处理 |
| 服务事件 | `incident.opened`、`incident.updated` | 事件负责人及受影响服务负责人；仍须有权阅读全部受影响服务；恢复后停止提示待处理 |
| 秘书结果 | `run.completed`、`run.failed`、`run.cancelled`、`run.interrupted` | 本次运行发起人；沿用会话受众及固定来源检查；失败、中断、等待补充或冲突等实际结果需要处理 |

事件的聚合类型和修订必须与当前业务对象一致。旧事件不会被重新解释为新的负责人或新审批步骤；失效事件、过期职责及无权接收者按当前事实抑制。业务来源已失效时，通知也不会提供旧标题或独立访问权限。

任务、事件等相同主题更新合并在一条通知中；审批步骤、账期、副本、合同提醒阶段另含准确上下文。订阅同一账期的多个提醒可以提高该通知的投递序号，持久提醒记录仍分别保留。

## 3. 已读与业务处理

通知具有 `delivery_seq` 和 `read_seq`。只有两者相等时才标为已读；业务状态单独决定 `attention_required`。

例如：员工打开序号 1 的页面后，序号 2 已到达。提交 `{"delivery_seq":1}` 只能确认第 1 次投递，通知仍为未读。确认第 2 次投递后变为已读；任务仍为 todo 时，它仍显示“仍需处理”。禁止确认尚不存在的未来序号。

已读命令使用现有幂等、审计和 Outbox 事务。相同确认可以安全重放；确认不改变通知排序、不修改任务或申请、不登记费用／付款。客户端保留未核对命令的请求键，跨分页合并时优先采用较新的投递与已读序号。

## 4. 数据与事务

迁移 `0052_in_app_notifications.sql` 新增以下记录：

| 表 | 用途 | 可变性 |
| --- | --- | --- |
| `notification_threads` | 本人通知头、业务主题、当前投递头和已读边界 | 仅按数据库守卫推进，身份不可改、已读不可回退，不允许删除 |
| `notification_deliveries` | 实际事件、接收人、模板版本、准确投递序号和执行租约 | 只追加 |
| `notification_job_results` | 实际投递／抑制数、安全结果码和任务租约 | 只追加 |
| `notification_due_events` | 合同生效修订、截止日、提前量、时区与实际 Outbox | 只追加，插入时核对当前生效内容和匹配事件 |

迁移包含 10 个通知守卫，其中 3 个为延迟约束。工作线程必须持有实际运行中且未过期的任务租约；通知头、连续投递序号、投递事实、实际成功任务及结果计数在事务结束时一致。伪造或过期租约、无匹配事实的通知头及修改历史证据都会失败。

服务按组织、接收人和业务主题取得事务级锁，避免并行任务产生相同序号。投递、通知头推进、任务结果和队列成功同事务提交；中途故障全部回滚。业务 Outbox 已先完成自己的事务，不受通知故障影响。

投递记录中的 `delivered` 仅代表进入站内收件箱；不会声称员工已读。`suppressed` 是本次已计算接收候选中被抑制的数量，事件已无当前接收候选时可以为 0；应结合 `outcome` 和安全结果码核对。

## 5. 当前授权和隐私

列表和概览在一致的数据库快照内检查当前组织／用户版本及业务 ACL，沿用任务、审批、合同、订阅、文件、服务、秘书各模块的正式读取校验。每条通知的资料标题、状态和职责来自当前业务记录；未通过检查的记录不进入列表或计数。幂等已读回执沿用现有业务命令的保存策略，重放前也须通过当前权限检查；两端确认后重新读取当前列表，不能把历史回执作为最新业务状态。

详情和已读只接受本人通知 ID。猜测他人通知、撤权资料及无权读取的投递异常返回统一不可用结果。实际资料页继续执行自身读取校验，客户端跳转不构成授权。文件通知仍检查当前祖先目录，服务事件仍检查所有受影响服务，秘书结果仍检查消息受众和固定来源。

新建 `notification_operator` 角色及 `notification.delivery.read` 动作，角色要求 MFA。迁移和新组织初始化均创建角色定义，默认不为任何员工绑定。异常接口只返回任务 ID、状态、安全结果码、尝试次数和时间，不返回事件正文、原始错误、标题、对象键或凭证。

## 6. API 与界面

| 方法及路径 | 输入和行为 |
| --- | --- |
| `GET /v1/notifications` | `state=all/unread/attention`、category、cursor、limit 1—50；拒绝未知或重复查询项 |
| `GET /v1/notifications/summary` | 本人未读数、仍需处理数、计数是否完整、数据库核对时间 |
| `GET /v1/notifications/{id}` | 本人通知及当前允许的资料地址 |
| `POST /v1/notifications/{id}/read` | `delivery_seq` 和请求幂等键，先检查当前资料权限再确认 |
| `GET /v1/notification-delivery-failures` | 指定运行管理动作；分页读取 notification 队列的 retry_wait／dead，以及本消费者的拒绝事件 |

列表一次最多核对 1000 条候选并返回续读游标。概览最多核对 1000 条通知头，未读或待处理数量超过 100 时封顶并返回 `count_complete=false`。两端显示 `100+` 等下界；未核对完整的零显示“待核对”，不能显示为确切零或宣称没有工作。

Web 通知和概览每 30 秒刷新，切回窗口按现有查询策略重新读取；Taro 在页面展示和员工明确刷新时重新核对，隐藏时清空页面资料并取消读取。当前没有把轮询表述为即时推送。任一读取错误都隐藏该次列表旧内容，避免继续呈现失效标题。

打开通知时，两端先读取当前通知详情，再校验固定的资源路由。任务打开对应项目的准确任务；秘书结果打开对应会话的准确运行，资料页还检查运行与当前会话一致；订阅账期打开对应账期。共享路由校验拒绝外部跳转、未知类型、缺失容器及 ID 与路径不一致。

## 7. 运行与配置

独立入口：

```powershell
python -X utf8 app/scripts/run_backend.py worker-notification
```

原生部署单元位于 `app/deploy/native/copypaste-notification-worker.service`。worker 只接收数据库、运行环境及三项合同提醒配置，不继承普通云存储、模型或 Telegram 凭证。

每轮最多分派 8 个事件、处理 1 个通知任务，循环间隔约 250ms。任务租约 2 分钟；每个任务最多 4 次尝试，前三次失败按 15／30／60 秒加 0—10 秒抖动退避，耗尽后进入可见异常队列。每分钟核对合同到期并清理耗尽任务。多实例沿用队列及业务主题锁，不保证事件全局顺序。

| 配置 | 约束 |
| --- | --- |
| `CP_NOTIFICATION_CONTRACT_ORG_ID` | 明确的公司组织 UUID |
| `CP_NOTIFICATION_CONTRACT_TIMEZONE` | 明确 IANA 业务时区，拒绝 Local |
| `CP_NOTIFICATION_CONTRACT_DAYS_BEFORE` | 1—12 个不重复的 0—365 天提前量，以逗号分隔 |

三项全部为空时关闭合同提醒；部分填写或无效值使启动失败。多个提前量已错过时，只补排当前最近阶段，避免停机后一次补发全部旧阶段。调度策略变更不会修改旧事实。当前开发配置保持未配置，订阅提醒继续沿用各订阅已经保存的账期、时区和责任人。

订阅账期和提醒仍由现有 `worker-subscription` 生成，notification worker 消费其实际 Outbox 并投递；部署时需分别启用两个原生服务，通知消费不代替账期生成。

## 9. 后续差异

GAP-08 继续保留：工作台尚须聚合更多业务待办／到期／异常，任务 @提及尚无正式生产者，生产备份失败尚须接通真实备份任务及提醒来源。通知偏好、跨渠道模板／回执、批量运维重放和更大规模负载验证仍待补齐；不以本次通知中心关闭全部通知或平台 Goal。

Telegram 股东群绑定、外部身份与群受众授权、真实跨境连通和消息回执继续由 GAP-15 推进，授权约束沿用 GAP-11。Android 原生宿主／大文件传输、微信／抖音真机及发布、实际双云与 120GB／2TB、生产 PostgreSQL／备份恢复也继续按原编号验收。
