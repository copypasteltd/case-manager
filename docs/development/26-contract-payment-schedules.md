# 合同收付款计划与固定履约节点

本章细化 OA-07/08，承接[合同草稿](23-contract-drafts-and-fixed-evidence.md)、[顺序审批](24-request-snapshots-and-sequential-approvals.md)和[签署生效](25-contract-signature-and-activation.md)。迁移 `0030_contract_payment_schedules.sql` 将计划纳入不可变业务修订，在明确生效事务中生成固定节点。实际费用、收付款、分配和冲销仍需财务模块接入；计划和应付金额均不能当作已付事实。

## 1. 三种计划情况

| 数据 | 含义与行为 |
| --- | --- |
| payment_schedule = null | 尚未整理；历史合同不会被推断出条款；不等于零义务或已结清 |
| mode = scheduled | 至少一个、至多100个收付款节点；币种和方向继承合同 |
| mode = no_payment | 明确无收付款义务；说明必填、节点为空、合同方向为 none 且总额为零 |

节点固定 id、title、amount、due_date、conditions。id 在同一计划中唯一；修改标题、日期、条件时保留节点身份。删去后重新建立节点产生新的标识。所有变化先写入新业务修订，不修改历史计划或已经生效的节点。

金额使用十进制字符串及币种精度目录，不使用浮点数。提供金额须大于零；全部节点金额已知且合同总额已填时，合计必须精确等于合同总额。税额属于合同总额，不在节点合计上再次叠加。节点不支持混合币种、负数或在计划中直接登记退款。

草稿节点允许金额、日期为空，以保留真实未知情况。非空日期必须有效，条件限20000字，标题非空且不超过200字。送审前，已列计划的每个金额和到期日均须补齐，合同币种、方向和总额须确认；未整理计划的旧数据可保留，但不构成未来结算/完成核对的通过依据。补充已批准合同条款须采用另行审批的补充协议，不能在签署后直接补写原计划。

## 2. 修订与兼容

新建和编辑业务修订使用 payload_schema_version=2。合同规范摘要的外层 schema 也为2，包含合同身份、范围、分类、主合同关系和完整内容；payment_schedule 随金额、条款、正文版本一起参与摘要。读取历史修订直接保留其原有摘要，不按新字段重新计算。

| 数据年代 | 兼容约束 |
| --- | --- |
| 合同修订 Schema 1 | payment_schedule 必须为 SQL NULL，原内容和摘要不变 |
| 合同修订 Schema 2 | 允许 null 或明确计划；新编辑只能追加此版本修订 |
| 既有申请快照 | 缺少 business_payload_schema_version；重新序列化时保留原 JSON 内容投影，省略新计划空字段 |
| 新申请快照 | business_payload_schema_version 固定准确业务修订的1或2；包含该修订计划 |

申请修订自身的外层 Schema 仍为1，新增业务版本标识是可选扩展。未携带新标识的旧快照在修订摘要计算中保持原表示；不能给历史快照补标识、改摘要或把旧批准解释为新计划已批准。独立兼容测试以旧完整 JSON 计算预期摘要，验证升级后重读结果一致。

普通合同响应始终返回 nullable 的 payment_schedule 和实际 payload_schema_version。完整 ContractPatch 必须包含 payment_schedule；明确清空传 null，不能通过漏字段意外删除已有计划。专用计划接口仅替换计划，但仍使用同一个合同修订、并发与申请失效流程。

## 3. 审批与生效事务

计划编辑取得当前合同更新权限，按项目、合同顺序加锁，核对 expected_version 与 base_revision_id，生成新修订及摘要、推进合同头版本。已有可编辑申请回到待重新核对的草稿，旧申请快照保持不变；更新申请、送审预览、最终提交仍为明确独立操作。

提交和审批展示、固定完整计划。制度选择、当前审批人、准确正文及往来方权限沿用既有审批协议；预览摘要同时绑定计划，不允许在预览与提交之间换节点。最后批准只进入待签署，不生成履约节点。

签署登记仍只记录签署事实。用户确认合同生效时，数据库在同一事务内从准确有效修订的计划按顺序生成 contract_milestones。每行保存独立记录 id、合同/有效修订、plan_item_id、位置、标题、方向、币种、金额、到期日及条件。应用不接受客户端另传一套执行条款。

数据库约束包括：计划形态与币种精度检查、正金额、唯一节点身份、已知合计一致；批准/生效阶段计划完整；履约行必须逐字段匹配准确有效计划；生效时必须有完整集合。履约行不允许更新或删除，不允许追加计划之外的节点。

生效事件、有效指针、全部履约行、审计、Outbox 和幂等结果同事务提交；审计失败时全部回滚。重试返回原结果，双设备竞争只允许一个合同头版本获胜。普通管理员仍没有自动业务读取权；列表先取得当前合同读取权限。

## 4. 接口

| 接口 | 契约 |
| --- | --- |
| POST /v1/contracts | 可传完整 payment_schedule；未整理传 null |
| PATCH /v1/contracts/{id} | 完整合同内容及准确基础版本；计划与总额可原子调整 |
| POST /v1/contracts/{id}/milestones | expected_version、base_revision_id、payment_schedule、reason；编辑草稿计划并返回新合同修订 |
| GET /v1/contracts/{id}/milestones | 取得当前可读合同的固定执行节点，按位置排序；最多100项，批准或签署后尚未生效时为空 |

专用 POST 路径保留“milestones”命名，语义是修改尚未生效的合同计划；它不会追加未经批准的履约行。非草稿返回 CONTRACT_READ_ONLY，旧基础版返回409，计划矛盾/缺项返回422，失权合同返回404。精确字段和响应以[机器契约](openapi.json)为准。

## 5. 页面与展示

编辑器提供“尚未整理”“按节点收款或付款”“明确无收付款义务”，逐行填写名称、金额、到期日与条件。金额错误保持全部输入，重新保存需重新核对；并发冲突继续遵守草稿版本保留规则。使用者不需要输入内部节点或修订标识。

合同、历史修订和审批快照共享计划展示。无计划显示“尚未整理”，无义务显示已记录说明；未知金额不渲染为零。生效详情另列“履约节点”，明确标为“应收”或“应付”。只展示到期日，不根据未知付款情况擅自显示“逾期未付”“已付款”或“已完成”。

样式使用官网继承的品牌、边框、字体与双主题令牌；小屏字段单列，金额与币种完整可辨，条件换行，长表单内部滚动。详见[组件约束](../design/03-components-and-patterns.md)。

## 6. 已执行验证与下一步

签署/生效隔离测试扩展到15个叶场景，其中4个新增场景覆盖计划精确修订与非法/不完整阻断、获批计划自动生成且不可改写、明确无义务、旧 Schema 1 保持及追加升级；原生审计回滚场景也覆盖自动节点回滚。另有旧申请摘要兼容单元场景。完整后端报告的时间与源码摘要见[实施台账](../delivery/02-implementation-ledger.md)。

[受控真实浏览器](../quality/evidence/business-execution/result.json)扩展为6条检查链，验证真实计划编辑、错误合计422与输入保留、稳定节点标识、精确送审快照、独立审批、本人 Web MFA 签署、生效后准确节点及现有未来日期/双设备冲突。双主题五宽度通过；390px浅色计划编辑和1440px深色履约详情已人工复核。检查结束关闭所有浏览器、释放自建原生数据库并停止所属临时 Vite。

后续财务模块须通过不可变实际收付款及有效分配计算履行金额；应付费用与实际现金支出分开，收款不得进入支出费用，冲销不得删除历史。合同完成/终止还需未结节点与相关项目/采购检查，不能仅以计划到期或零节点决定。真实云、120GB、银行与电子签名均不属于本章受控证据。
