# 合同签署登记与生效

本章承接[合同草稿](23-contract-drafts-and-fixed-evidence.md)和[合同顺序审批](24-request-snapshots-and-sequential-approvals.md)。迁移 `0029_contract_signatures.sql` 与 contracts 服务实现批准后的签署事实登记和明确生效。[收付款计划与固定节点](26-contract-payment-schedules.md)已后续接入；完成/终止核对与财务关联继续开发，不能把本章登记能力当作整个合同管理闭环。

## 1. 三条事实

申请最后一步批准后，合同进入 pending_signature，approved_revision_id 固定准确合同业务修订；active_revision_id 仍为空。签署由有权人员另行登记，不调用电子签名服务，也不代表系统出具法律结论。

签署登记固定合同修订、准确批准申请修订及实例、真实签署日期、准确签署件版本、登记依据、条款核对说明，以及实际人工会话和近期 MFA 证据。签署日期不能晚于香港当前日期；生效日期直接固定已批准修订的起始日期，不由签署表单覆盖。没有签署件例外制度时不能空件登记。

签署登记本身不激活合同。达到批准日期后，由登记人核对当前正文/签署件与主合同状态，再明确确认生效。该操作追加生命周期事件并设置 active_revision_id；不是付款、费用确认、结算或履约完成。达到到期日不自动写成已完成或已终止；历史签署事实和法律效力由业务核对，模型不作法律判断。

## 2. 数据与数据库边界

| 对象 | 关键约束 |
| --- | --- |
| contract_signatures | 合同及修订唯一签署登记；准确申请/实例复合外键；签署件、日期、说明、登记人/会话和 MFA 均固定；仅追加 |
| contract_lifecycle_events | 当前实现 pending_signature→effective；准确合同修订及签署记录；同修订生效事件唯一；仅追加 |
| file_version_references | 新增 contract_signature 类型，签署件在登记事务中获得引用保护；保留页面显示“合同签署件” |
| contracts | 草稿不能声称已批准或有效修订；非草稿不能普通覆盖正文或回收；有效修订不能清空/替换 |

登记触发器检查准确业务批准链、当前阶段和已批准生效日期。生效延迟约束同时检查准确签署件登记、生命周期事件、有效指针和已到生效日；补充协议还要求有效主合同。尚未接入的完成、终止等状态迁移被明确阻断，不能绕过未结节点核对。

主合同与补充协议分别保存批准和有效修订。补充协议生效前，主合同继续使用原有效修订；生效后也不通过普通编辑覆盖主合同原件或历史。

## 3. 权限、事务与重放

新增独立未绑定角色 contract_operator，包含 contract.read/contract.execute 并要求 MFA。原合同草稿管理权限不自动带来签署与生效权限。签署和生效只接受本人 Web、Android、微信或抖音会话，实际数据库会话、设备和近期 MFA 在幂等重放之前重新核对；Agent 不能以伪造验证时间执行。

命令沿用组织授权、用户、项目、合同锁顺序和准确头版本。登记/生效重新检查当前往来资料读取、批准正文和签署件的可用性、权限、分类/范围及扫描/例外证据。引用不自动授予读取权；补充协议生效还要求读取主合同。

签署记录、签署件引用、头版本、审计、Outbox 与幂等结果同事务提交。生效事件、有效指针及对应审计也同事务提交。任何失败回滚全部新增事实，允许同键安全重试。两设备竞争只允许一个头版本获胜；同键重放返回原签署或生效结果，不能再次执行。

重放保留原业务结果，但重新隐藏当前无权限的正文/签署件名称，并清除过期动作能力。普通响应不暴露实际会话 ID、MFA 内部证据、对象 Key、云凭证或下载签名。

## 4. 接口

| 接口 | 输入与结果 |
| --- | --- |
| POST /v1/contracts/{id}/signature | expected_version、revision_id、content_hash、signed_on、signed_file_version_id、attestation、reason；201 返回合同与固定签署记录 |
| POST /v1/contracts/{id}/transition | 当前 action 仅 activate；另需准确头版本、合同修订/摘要、signature_id 和 reason；200 返回当前有效合同 |
| GET /v1/contracts/{id} | 返回 signature 及 can_register_signature/can_activate；签署件详情各自重新授权 |

生效日期未到返回 CONTRACT_NOT_YET_EFFECTIVE；已有签署登记返回 CONTRACT_SIGNATURE_EXISTS；缺少签署依据或主合同未生效分别明确阻断。一般版本冲突保留表单，由使用人重新核对，不自动更新基础版再执行。

## 5. 页面与验证

合同详情按固定批准修订展示批准后的资料，签署区显示实际签署日、批准生效日、登记日及说明。签署件使用共用正式版本选择器，选择准确历史版本；下载继续使用固定版本授权。MFA 内嵌表单，验证成功仍需手动确认。双主题、小屏内部滚动和状态语义遵守[组件设计约束](../design/03-components-and-patterns.md)。

11 个隔离原生 PostgreSQL 叶场景已通过：准确批准链、未来签署日期、签署与引用固定、提前生效阻断、明确激活、两个并发登记/生效、旧结果重放、主从合同、签署/生效审计回滚、实际会话 MFA 与 Agent 阻断、当前文件失权及关联信息重新隐藏。正式文件来自受控提供商，不是实际云或真实法律签署。

Web 正向执行使用专用隔离数据库与受控正式文件，由独立检查脚本验证真实页面和 API。证据必须注明人工 Web MFA、受控提供商及数据库清理情况，不能混入真实 OSS/R2、120GB、银行或电子签署验收。全量报告以[实施台账](../delivery/02-implementation-ledger.md)的执行时间与源码摘要为准。

[受控浏览器记录](../quality/evidence/business-execution/result.json)的 6 条检查链已通过（含后续收付款计划扩展）：完整固定送审、独立账号决定、真实 Web MFA 登记签署件、单独生效确认、未来合同阻断及第二设备冲突保留。两主题五种宽度、零脚本/服务端错误；全部浏览器关闭，原生夹具退出码为0，隔离数据库清理及所属 Vite 停止均已确认。390px 浅色签署弹窗与1440px深色签署详情已人工复核；嵌套弹窗焦点恢复已修正，不残留页首跳转链接焦点。此证据使用受控正式文件与虚构制度，不属于真实云及法律签署证据。
