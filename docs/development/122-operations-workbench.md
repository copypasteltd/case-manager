# 增量122：服务事件与文件存储待办 / Operations workbench

本轮补齐两条实际业务链路：负责人从首页进入服务事件，追加解决记录后退出待办；文件创建者从首页进入存储详情，人工重试已有失败副本，等待完整校验后退出待办。Web、微信、抖音及 Android 共用同一汇总协议，移动端新增了原先缺少的副本重试表单。

This increment connects assigned incidents and creator-owned storage work to the existing business desk. Resolve an incident through its ordinary editor; retry an existing failed replica through file details. Refreshing removes work only when its current business condition is satisfied. The Taro source is shared by WeChat, Douyin and Android.

## 1. 使用流程

| 编号 | 入口 | 操作 | 完成依据 |
|---|---|---|---|
| OPS-01 | 首页 → 我负责的未结事件 | 打开事件，核对影响范围，追加进展与实际解决说明，按原有规则完成身份验证并确认 | 当前事件为 `resolved`；历史时间线继续保留，下一次首页读取排除该事件 |
| OPS-02 | 首页 → 我创建的文件存储待办 | 打开文件，选中失败／缺失副本，填写原因，明确安排复制 | 返回同一副本的下一修订及 `queued` 回执；首页继续显示待验证 |
| OPS-03 | 文件复制 Worker | 按原有队列、租约和完整摘要规则执行复制 | 当前正式版本的已有 OSS／R2 副本均有有效校验证据，且内容可用，下一次首页读取移除待办 |
| OPS-04 | 任一详情处理后回首页 | 刷新业务待办；移动端返回首页会重新读取 | 当前权限、负责人／创建者、正式版本与状态重新计算，不沿用旧操作按钮的判断 |

事件解决并不代替监控恢复观测；副本排队也不等于对象已复制。首页提供业务入口，实际写入仍经过原来的事件／文件 API、幂等、版本冲突、授权、审计与队列规则。

## 2. 汇总协议与查询约束

`GET /v1/dashboard/business` 现在固定返回五组：`approvals`、`contracts`、`subscription_periods`、`incidents`、`file_attention`。原三组语义保留。每组先计算整个当前授权集合的数量，再返回最多五条，`has_more` 明确表示还有记录；对应业务列表继续提供详细查阅。服务端不接受调用者传入负责人、组织、分页上限或任意查询条件。

原有只读事务、五秒截止时间、组织／用户权限版本锁、交互会话前后复查及四个人工渠道限制继续生效。秘书运行与 TG 执行身份不能读取这份个人首页快照。新查询不产生事件、不标记已读、不自动发起重试。

### 服务事件

- 必须属于当前组织，由当前用户担任登记负责人，并处于 `open`、`investigating` 或 `monitoring`。
- 一到二十个受影响服务必须全部存在，且全部通过当前渠道的 `service.read`。失去其中一个服务权限时，整条事件及其数量都隐藏。
- `revision_id` 是 `incident_timeline` 中与当前事件 `version` 对应的真实不可变记录编号；不构造占位编号、不伪造到期日。
- 登记人不替代负责人；已解决事件不继续占用首页待办。实际编辑仍使用近期 MFA、版本条件和不可变时间线。

### 文件存储

文件目前没有事件式的可转派负责人。本组明确使用 `files.creator_id`，界面显示“我创建的文件存储待办”，不把当前上传者、其他阅读人或管理员推定为负责人。

- 只统计当前正式版本；`revision_id` 固定为实际 `current_version_id`，历史版本的失败不覆盖新版本状态。
- 文件必须为 `active`、当前具有 `file.read`，且整个目录祖先链处于 active 并到达根节点。使用与普通文件列表相同的项目、分类、渠道与创建者授权依据。
- 一个文件只计一次；排序时间包含当前版本副本的最新更新时间，避免复制状态变化一直落在旧文件排序中。
- 不返回桶、对象键、提供商原始错误、正文、扫描内容或其他用户的工作。文件名继续作为普通文字渲染。

| 显示状态 | 判定顺序与含义 | 消除条件 |
|---|---|---|
| 当前版本不可用 | 可用性不为 available，或扫描处于 quarantined；优先于副本状态 | 正常文件流程恢复可用条件，副本也不再需要处理 |
| 副本需要关注 | 已有副本失败、缺失、等待重试、关联任务停止／耗尽；verified 标签缺少准确摘要／校验时间；或已有记录只覆盖一个存储端 | 后续受控流程补全并核实实际副本，不能只改展示标签 |
| 副本待验证 | 已有副本处于 queued／copying／verifying 等尚未完成状态 | 两端已有副本均提供有效完整摘要及校验时间 |

没有任何副本记录且内容可用的旧文件，不在本轮被推定为“异常”或“备份健康”；普通详情仍显示尚无副本资料。缺少副本行、缺失主端或校验证据不一致，也不代表现有重试 API 能自动修复。本轮闭合的是已有可重试副本的正常人工恢复链路；存储管理与真实云验收继续在 GAP-07／20。

## 3. 四端实现

| 部分 | 实现 |
|---|---|
| Go | `backend/internal/workbench/service.go` 在同一事务内汇总五组；复用现有事件、文件、复制服务，不新增数据库结构 |
| 协议 | 生成的 OpenAPI／TypeScript 类型固定五组和允许状态；共享校验拒绝重复分组、虚假数量、错误日期、已解决事件及健康文件假待办 |
| Web | 首页动态显示两组；继续使用原事件编辑器和文件重试窗口；重试改用共享输入及回执核对 |
| 微信／抖音／Android | 首页进入 `/pages/status/index?kind=incident&id=…` 或可操作的 `/pages/files/index?file_id=…`；新增副本重试表单、明确确认及回执 |
| 重试一致性 | 共享模块固定当前副本修订、限定原因长度；返回必须是同一编号／提供商、下一安全整数修订、queued，旧摘要／校验时间／错误必须清除 |
| 并发／失败 | 保留原幂等键和版本冲突。移动端结果未确认或权限变化时停止重复提交，要求重新读取；隐藏页面后清理当前表单与回执 |

移动端重试遵循原 Web／API 的授权和会话规则；事件编辑的近期 MFA 要求保留。本轮没有增加 AI 费用控制，也没有降低隔离、审计或技术资源限制。

## 4. 验证与发布边界

详见[实际检查记录](../quality/122-operations-workbench-verification.md)。本轮使用范围明确的后端集成回归、完整 Web／共享移动单元测试、类型检查、小程序编译，以及实际 Web／Taro H5 页面和原生临时 PostgreSQL／API。复制失败来自受控提供商返回的错误字节，恢复流程执行真实队列 Worker 和完整字节摘要核对；并非把 API 响应替换成成功。

采用显式 `scoped_increment` 发布检查：当前功能源码、实际执行的检查及页面分别绑定；增量121完整回归和 Android 开发 APK 保留原提交及原字节。本轮不把旧 APK 标为122，也不声称重新执行完整后端／Linux／模型／平台／生产验收。正常结构仍为93，所有原迁移文件保持原字节。

GAP-08／18获得本轮子功能；实际公司规则、真实云故障来源、跨渠道送达回执、更多首页聚合及完整业务验收继续开放。原28个编号、23项待完成（14 P0／9 P1）、5项移出，以及八项 draft Skill 保留。
