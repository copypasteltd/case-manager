# 秘书新建文本文件、准确授权与正式首版本

本增量推进 GAP-04／11／12／13／18，补上秘书在指定目录新建文本文件的实际业务链路。后端、MCP、共享契约、Web 与 Taro 代码位于 `app/`；验收证据见[验证记录](../quality/evidence/secretary-file-creates/verification.md)，全部待完成项保持在[28项差异表](../delivery/03-goal-gap-assessment.md)。

## 1. 首期范围与授权

| 项目 | 当前约束 |
| --- | --- |
| 授权入口 | 本人私密公司／项目会话；用户选择实际目录、准确名称与格式，确认发送消息后固定本次新建意图 |
| 支持内容 | UTF-8 文本 `.txt`／`text/plain`、Markdown `.md` 或 `.markdown`／`text/markdown`；扩展名与类型必须匹配 |
| 大小与编码 | 1 至 49,152 字节（48 KiB），不接受无效 UTF-8、NUL、裸 CR 或混合 LF／CRLF；可保留 BOM 与一致的换行 |
| 对象范围 | 目录归属与会话项目一致，分类不超过会话上限；保留目录原有分类，不借新建改变权限 |
| 业务权限 | 原 `folder.read`、`file.upload`、AI 处理许可及项目可写状态；模型不能提供有效身份或自行换目录 |
| 写入数量 | 每个运行最多暂存3份独立草稿，最多提交1个正式文件；草稿不构成新文件 |
| 冲突处理 | 同名文件或目录均冲突；保留原资料，修改名称或重新核对目录后发起新请求 |

这是 L1 少量可恢复写入：用户确认发送准确新建请求即构成本次授权，不额外发起一次 MFA 计划批准。选择目录或填写名称本身不发送请求。批量目录整理继续沿用[增量55](55-secretary-directory-organization.md)的准确计划与近期 MFA 批准，不能把单文件授权扩展为批量或跨范围授权。Telegram、共享会话和任意二进制／Office／PDF 新建未开放。

48 KiB 是本次新建正文上限；工具请求总 JSON 仍受64 KiB限制，包含转义及结构开销。现有文件正文更新的1 MiB上限保持独立；120 GB上传需求继续由普通文件上传链路承担。

## 2. 固定请求与来源

沿用 `POST /v1/conversations/{id}/runs`，新增可选 `file_create`：

```json
{
  "folder_id": "实际目标目录UUID",
  "expected_folder_version": 3,
  "name": "项目会议纪要.md",
  "media_type": "text/markdown"
}
```

运行的完整请求仍包含会话版本、安全版本、运行配置、客户端消息ID和消息正文；`file_create` 与 `file_update`、其他 mutation 输入互斥。上述片段仅表示新增字段，不是可直接提交的完整请求。

服务器读取目录真实归属、分类、元数据版本及最多32层祖先路径，固定发起人／组织认证权限版本、会话修订、安全版本、请求正文和目标摘要。用户消息保存 `agent_file_create` 来源及准确意图 SHA-256。历史来源引用只可核对，不能授权另一轮写入。

新建不伪造现存 `file_id` 或 `base_version_id`：数据库两者为 NULL，模式为 `create`，基础文件版本为0；返回 `run.file_create`，现有更新仍返回 `run.file_update`。`authorized`、草稿或拟定结果均没有正式操作凭证。

每次执行检查当前权限、AI许可、项目状态、目录版本及祖先摘要。同名检查与正式提交复用原命名空间锁；暂存期间目录变化、撤权、运行取消或过期都会阻止后续写入。云端I/O之后重新鉴权，不能依赖I/O之前的一次判断。

## 3. MCP 工具与提交过程

| 工具 | 必需参数 | 结果 |
| --- | --- | --- |
| `stage_file_create` | `folder_id`、`name`、`content` | 从空正文计算真实差异、字节数及内容摘要，建立独立草稿上传并暂存；不创建正式文件 |
| `propose_file_create` | `folder_id`、`name`、`draft_id` | 固定本次意图、目录依据、草稿内容和真实暂存来源，返回准确计划摘要 |
| `commit_file_create` | `folder_id`、`name`、`draft_id`、`plan_hash` | 仅提交准确已暂存、已完成原扫描与提升链路的草稿；返回真实业务回执 |
| `read_resource` | `type=agent_file_create`、准确运行ID及分页参数 | 按当前权限核对不可变原意图与当前结果 |
| `inspect_operation` | 当前 `run_id` | 核对创建状态与真实操作凭证 |

新建运行不能调用原文件更新工具，原更新运行也不能调用新建工具。`file-update` 运行配置的准确允许工具集合为读来源、查操作、原更新三项及新建三项，共8项；没有批准、任意文件系统、Shell或云凭证工具。

暂存沿用独立上传会话、容量和存储epoch约束。完整性校验、扫描及对象提升继续经过原上传worker；没有扫描成功时只能返回待处理，不能提交或虚报已完成。差异保存真实新正文，预览最多1000个Unicode字符，并明确是否完整。

正式提交复用 `CommitAgentDraft`，基础版本为 NULL，生成真实文件及第1个正式版本。内部业务标识为 `/internal/agent-files/create`，幂等键为 `agent-file-create:{run_id}`；这不是新增公开HTTP路由。

文件、首版本、复制记录、审计、Outbox、业务幂等凭证和工具提交凭证在同一个PostgreSQL事务内产生。任一凭证失败则全部回滚。重复提交准确相同内容仅返回原回执，不再创建文件。只有实际成功的本轮 `commit_file_create` 凭证与对应操作引用才能证明运行完成。

## 4. 历史、权限与存储事实

历史读取继续检查原始受众、当前目录读取／AI许可、当前项目及分类上限；已提交时再核对正式文件版本的当前访问权限。原目录改名后仍可按权限核对已完成历史，不能用历史目录版本变化抹去事实，也不能凭历史快照绕过当前权限。

创建回执包含真实 `file.id`、`file_version.id`、`seq=1`、空基础版本、`source=agent`、扫描状态、正文摘要和原业务 `operation_id`。第二存储副本保持真实 queued／复制／校验状态；正式首版本提交不等同于 OSS 与 R2 均已校验。

迁移 `0055_agent_file_creates.sql` 扩展原不可变意图表的模式及可空基础ID，默认仍为 `update`。旧更新行表示不改写；模式约束分别要求更新具有真实基础版本、新建无基础ID且目录版本为正。原13项文件证据触发器继续约束准确目录／草稿、消息来源、扫描后的首版本、业务路由及对应提交工具凭证。应用身份仍不能更新或删除五类文件意图／草稿／暂存／计划／提交证据。

## 5. 两端行为与交付契约

Web 与 Taro 会话均可浏览可读根目录／子目录，输入准确新名称与格式，将新建意图加入本次请求，确认发送后查看授权、草稿和实际结果。新建选择与现存文件更新互斥；取消未运行的任务不产生正式文件。移动端公共页面仍13个，入口位于原秘书页面。

两端共享 `makeFileCreate` 与 `fileCreateReceipt`，核对目标目录版本、名称、格式、意图、草稿计划、内容摘要、扫描状态、正式首版本和操作凭证，避免把更新回执或其他运行结果当新建成功。新建展示从空正文产生的真实内容，不渲染虚构的旧文件。

[OpenAPI](openapi.json)当前为250条路径、314项操作、535个Schema。本增量新增字段与结构，未新增公开路径。生成共享API类型与嵌入Go的OpenAPI保持一致。`file-update` 源码包为 `1.1.0`，SOP见[文件处理Skill](../skills/file-update/SKILL.md)；八项Skill仍为draft，实际发布和安装验收独立完成。
