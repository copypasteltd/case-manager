# 合同草稿、修订与固定依据

本模块承接 [OA 需求](../requirements/04-workflows-and-oa.md) 与 [审批协议](21-oa-approval-and-business-revisions.md)。当前实现合同草稿、不可变修订、固定往来方/正文依据、补充协议关系及 Web 管理。申请送审、顺序审批、签署登记、履约节点、终止与结算仍须继续接入；保存草稿不代表业务批准、签署或付款。

## 1. 头与内容分离

`contracts` 保存组织、业务编号、可选项目、不可变创建人、主合同关系、分类、业务生命周期、审批状态、当前/批准/生效修订指针、申请指针、回收时间和乐观锁版本。`contract_revisions` 保存完整结构化内容、序号、基础修订、Schema 版本、规范内容摘要、作者、依据与时间。修订只允许追加；当前、批准和生效指针必须引用同组织、同合同的准确修订。

编号由 PostgreSQL 序列产生 `CP-C-<序号>`，有组织内唯一约束，允许事务失败留下空号。禁止用 MAX+1，禁止截断长序号。普通编辑不能修改组织、项目、分类、创建人、主合同关系或创建时间；范围变更须独立评估流程。当前严格受限资料创建明确拒绝，不能绕过独立对象授权。

草稿至少填写标题、分类及创建依据，其余未确认事实可以留空：币种、金额、税额、收付方向、负责人、日期、相对方与正文版本均允许 null。`0` 是已知金额，不能用它代替未知。业务类别、续约/终止条款及说明允许空文本。负责人不等于创建人，分配负责人不会扩大本人范围权限。

## 2. 完整内容修订

编辑以 `expected_version` 和 `base_revision_id` 为并发依据，完整替换内容字段并追加修订。精确 PATCH Schema 要求所有内容字段，nullable 字段明确使用 null；不能因遗漏字段而猜测是否清空。过期版本返回冲突，不能自动改成最新基础版重试。

金额使用十进制字符串、数据库 numeric(20,6)，不经 JavaScript Number 或 float 计算。填写金额或税额前须有支持的币种，并按币种精度验证；税额包含在总额中，不能高于总额。日期使用真实 ISO 日历日，结束日期不能早于起始日。正文保存摘要绑定 Schema 版本、合同 ID、项目、分类、主合同及全部规范内容，引用的当前展示名称不参与替换摘要。

组织授权锁、项目锁、合同头锁按固定顺序取得。保存前重新鉴权及校验项目写入状态；头版本、修订、固定文件引用、审计、Outbox 和幂等结果在一个事务内写入。云读取、通知、OCR、模型及付款均不进入这个事务。

## 3. 固定往来方与正文

往来方必须同时指定准确对象 ID 和资料修订 ID。新增引用要求对象使用中、操作者当前可读、修订属于准确对象，资料分类不高于合同，范围为同项目或公司。已有准确引用可以在对象归档后继续保留；重新选择使用中的对象采用被明确选择的修订，不追随主资料自动更新。名称展示从固定修订读取，并再次校验当前 `party.read` 权限；无权读取时不泄露名称。

正文引用准确正式文件版本，核对同组织、活跃文件和目录树、available 状态、clean/waived 依据、来源项目与分类、当前文件读取权限。保留准确原始名称、版本号、字节数字符串、SHA-256、媒体类型和扫描例外标识；不返回对象 Key、云身份或签名地址。读取元数据不等于已经验证云对象实时可达。

每个带附件的合同修订在同事务登记 `file_version_references`，owner_type 为 `contract_revision`，owner_id 为准确业务修订。后续移除当前正文引用不会释放旧修订依据。历史引用保护不能通过编辑当前草稿绕过；物理清理与显式引用释放规则见 [保留协议](20-retention-and-reference-protection.md)。

合同权限不会自动授予往来方或文件权限。关联内容失去权限、回收或不可用时，合同仍可展示有权读取的结构化内容，关联名称/正文证据分别隐藏；后续新引用和送审必须重新校验。下载复用固定文件版本的独立授权与流式保存，不能从当前文件指针推断签署正文。

## 4. 生命周期与补充协议

头保留两条状态线，当前只创建 `lifecycle=draft`、`approval_state=not_submitted`。可编辑状态检查已保护正在审批、批准、生效等阶段，但这类状态的真实进入仍需后续申请与签署流程。隔离测试中的保护夹具不是实际审批完成证据。

补充协议创建时固定主合同，必须具有同组织、同项目和同分类，主合同可读且未回收。主关系不可原位修改，避免循环。主合同未回收的补充协议会阻止主草稿回收；恢复补充协议前主合同也须可访问且未回收。并发创建/回收通过共享与排他头锁保证关系检查。

回收只允许尚无申请、批准或生效记录、未送审的草稿。回收与恢复只修改头状态及版本，保留当前修订、全部历史、文件引用与审计；没有物理删除合同接口。项目 closing/archived/cancelled 时停止业务写入。

## 5. 接口与列表选择

| 接口 | 当前能力 |
| --- | --- |
| `GET /v1/contracts` | 按权限先筛选，再按更新时间/ID分页；支持标题/编号字面查询、项目、阶段与回收范围 |
| `POST /v1/contracts` | 创建不完整草稿和首修订；可固定主合同、往来方修订和正文版本 |
| `GET /v1/contracts/{id}` | 当前头与当前草稿，关联名称须各自授权 |
| `PATCH /v1/contracts/{id}` | 完整内容新修订、准确基础版和乐观锁 |
| `POST /v1/contracts/{id}/trash` | action 为 trash/restore；均要求版本与原因 |
| `GET /v1/contracts/{id}/revisions` | 读取权限加编辑权限，准确合同范围分页 |
| `GET /v1/contracts/{id}/revisions/{revision}` | 同组织、同合同的准确不可变修订 |

新建独立未绑定角色 `contract_manager`，含 read/create/update/archive；配置管理员没有自动合同读取权限。创建要求 create 与 read，历史要求 read 与 update，回收/恢复要求 read 与 archive。幂等重放前重新鉴权，撤权后旧结果不能作为内容访问渠道。

文件和往来方列表新增 `company_only=true`，在数据库分页前限制项目为空；不能与 project_id 同时指定。该筛选纳入游标绑定，不能跨范围复用游标。布尔查询只接受单个 true/false，拒绝空串、1、重复值等歧义。省略 company_only 维持全部有权读取资料的列表语义。

## 6. Web 与视觉约束

列表分别展示合同阶段和审批状态，未知金额标“未填写”。编辑器支持不完整草稿、明确清空、固定往来方选择、按项目/公司查找的文件历史版本选择、修改依据和冲突保留；不要求用户输入 UUID。补充协议入口继承主合同安全范围，不自动继承未经核对的金额或义务。

详情与历史展示准确修订的正文，下载前由服务端重新授权。尚无正式版、不可用或分类较高的文件在选择器显示原因；扫描例外用文字加语义警示。使用官网继承的品牌强调色、双主题语义令牌与共享原生模态框，小屏长表单内部滚动，不把草稿保存文案写成审批成功。

## 7. 验证边界

9 个隔离原生 PostgreSQL 叶场景覆盖公司筛选/游标、nullable 草稿、固定资料/文件与摘要、金额/日期、权限与跨范围、不可用正文、并发更新、主从回收顺序、审计失败回滚以及撤权后幂等结果关联资料的重新隐藏。文件提供商为受控测试适配器，不代表真实 OSS/R2 可用或 120GB 已传输。

真实 Web 验证使用明确虚构的项目、往来方与合同及结束即撤销的项目授权。实际结果见 [浏览器记录](../quality/evidence/contracts/result.json)。正文正向选择及下载需要真实合格文件；当前浏览器只验证无文件分支，固定正式正文的正向验证来自隔离数据库测试。全部自建浏览器必须关闭，不运行虚拟化环境。

当前浏览器记录有 6 条真实 API/UI 检查链通过，双主题、5 个宽度、零脚本及服务端错误；两项临时项目授权均撤销，全部浏览器已关闭。390px 浅色编辑表单及 1440px 深色详情截图已人工复核；移动表单内部滚动，后续操作可达。

申请已接入[固定快照与顺序审批](24-request-snapshots-and-sequential-approvals.md)。can_prepare_request 由当前实际权限及业务阶段推导；普通编辑已有关联的草稿/退回/撤回申请时，只使申请回到 draft，不覆盖旧申请修订。审批中编辑及批准后的阶段保护由真实审批实例测试覆盖，不通过伪造 request_id 测试。签署登记与明确生效已由[签署实施](25-contract-signature-and-activation.md)接入，履约节点和财务关联继续开发。


合同业务修订已由[收付款计划协议](26-contract-payment-schedules.md)扩展到 Schema 2；Schema 1 历史内容和摘要保持不变，新写入同时固定完整计划。

移动公共客户端后续已补齐完整合同草稿、真实往来方／正文版本选择、收付款计划及明确申请操作，见[移动业务草稿与送审](47-mobile-business-drafts-and-submission.md)及[相应设计](../design/20-mobile-business-drafts-and-submission.md)。实际UI与源码证据单独保存；移动签署、生效、履行和完整四端验收仍按各自能力矩阵推进。
