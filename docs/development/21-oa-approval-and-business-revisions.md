# OA 业务修订与顺序审批实现协议

本协议承接 [OA 需求](../requirements/04-workflows-and-oa.md)、[财务需求](../requirements/05-finance-and-subscriptions.md) 和 [数据字典](02-data-dictionary.md)。流程制度、合同申请快照和顺序审批已实现；具体能力及证据见[申请实施](24-request-snapshots-and-sequential-approvals.md)。合同签署/履约、采购、报销及财务闭环继续开发，不能把下文全部标成已实现。审批身份、金额阈值、本人审批制度及财务口径仍由 Q-06/Q-07 决定；开发提供明确配置入口，不替公司发布制度。

## 1. 三种修订与两条状态线

文件版本固定原件字节。合同、采购、报销各自的业务修订固定结构化内容、明细、金额、币种和附件版本；业务修订不能只存一个可变文件链接。申请修订再固定送审业务修订及流程快照，审批实例和决定始终引用准确申请修订。

业务生命周期与 approval_state 分开：批准不是已签合同、已收货、已付款或已结算。原币金额使用十进制字符串，数据库使用 numeric；业务编号由受锁计数器或序列分配并有唯一约束，允许空洞，不用 MAX+1。

草稿允许缺少送审必填项。草稿内容也保存不可变修订，编辑需要头版本和基础修订；空值与未提交字段在 PATCH 中区分。存在送审实例时，不能把修改写到正在审批的快照里。重提创建新申请修订和新实例；旧步骤、快照和决定保留。拒绝是原申请终态，后续需新申请。

## 2. 已发布流程选择

流程定义包含稳定 key、修订号、启用状态、业务类型、路由类别、币种、含下界/不含上界金额区间、顺序步骤、每步指定用户、MFA要求、本人审批制度、撤回制度和发布原因。首版只实现顺序步骤，不用含糊的“管理员”代替准确审批人。

发布使用独立配置权限、有效人工会话和最近 MFA。定义不可原位修改；停用也发布新修订。提交只选每个 key 的最新已发布修订，旧实例继续使用其固定快照。未配置、未匹配或同时匹配多条规则均明确拒绝，不能自动选择第一条或跳过审批。

币种目录中的精度是格式约束，不是公司基础币种决议。公司采用的币种、明细舍入和确认口径须由对应制度明确；跨币种金额不得直接比较。涉及尚未确定的计算/制度时，保留草稿并阻断送审或财务确认，不写入假默认值。

### 2.1 已实现的制度接口与持久化

迁移 `0025_workflow_definitions.sql` 保存不可变定义与规范化步骤。定义本身还固定完整步骤 JSON；插入子步骤时逐项核对父定义，延迟约束在提交时核对数量及连续顺序，防止后续通过追加 INSERT 篡改已发布流程。制度、步骤只允许追加，不允许修改或删除。

| 接口 | 行为 |
| --- | --- |
| `GET /v1/workflow-definitions` | 按 key 返回最新修订；可按业务类型筛选；游标绑定身份及授权版本 |
| `POST /v1/workflow-definitions` | 提交完整规则和 expected_version，新增不可变修订；发布须 config.manage、有效人工会话与近期 MFA |
| `GET /v1/workflow-definitions/{id}` | 读取准确发布修订 |
| `GET /v1/workflow-definitions/{id}/history` | 分页读取相同 key 的全部修订 |

组织授权锁串行化发布与规则重叠检查。区间为 `[min_amount,max_amount)`，上界 null 明确表示无上限；相邻边界可共存。类别为准确代码，`*` 明确表示全部类别；不同 key 的当前启用修订若类型、币种、类别相交且金额重叠，则拒绝发布。没有以类别优先级偷偷覆盖通配规则。

发布新修订需要上一修订号；停用同样新增修订。启用规则只接受本组织有效审批人，停用修订允许保留已停用审批人的身份，避免无法退役旧规则。同一规则不可重复指定同一个人。步骤绑定的成员 ID 不变，列表显示的姓名与有效状态取当前账号资料；历史页面明确说明这一点。

内部流程选择器检查最新启用修订、金额精度、唯一匹配及审批人可用性；已由合同申请提交与送审预览调用。发布不生成审批实例，不产生业务批准。审计、outbox、幂等结果、定义/步骤及授权版本递增在同一事务内；幂等重放前检查实际数据库会话和当前权限。

Web 路径 `/workflows` 使用现有品牌面板、语义状态、模态表单与内嵌 MFA；本人审批、撤回制度和金额下界须明确选择/填写，新建表单初始不启用。可添加、移除及重排准确审批人，冲突保留填写内容。规则代码稳定，修订历史可查。

8 个隔离 PostgreSQL 叶场景覆盖边界、精度、重叠、并发、不可变步骤、退役、停用审批人、审计回滚与重放前鉴权。[真实 Web 检查](../quality/evidence/workflow-definitions/result.json)记录 5 条检查链、双主题五种宽度、顺序重排及取消草稿；没有向开发公司发布任何审批制度，该制度页面检查不包含申请批准链；后续申请验证见独立实施章节。浅色 390px 与深色 1440px 截图已人工复核，所有检查浏览器均关闭。

## 3. 送审事务

按组织授权锁、业务头、申请头的固定顺序取得锁，重新验证操作者、范围、渠道、头版本及基础修订。然后在同一事务内：

1. 验证版本化 Payload Schema、送审必填、金额与明细合计、日期和业务关联。
2. 核对每项附件属于同组织/文件的准确版本、可用状态、扫描或例外依据及操作者读取权限；引用不得自动授予审批人文件读取权。
3. 选取唯一有效流程，核对指定用户状态、范围权限、本人审批制度和适用渠道；缺失或停用不自动替换。
4. 固定完整业务内容、附件摘要/风险状态、规则与步骤，计算规范 JSON 摘要。
5. 新建申请修订、审批实例和步骤，第一步 active，其后 pending；把申请原子改为 in_review。
6. 登记 approval_snapshot 固定文件引用，以及审计、Outbox 和幂等结果。任何失败全部回滚。

云、OCR、模型、通知和付款调用均不进入该事务。提交只建立业务与审批事实，不制造签署、费用已确认或银行已付款的事实。

## 4. 决策与并发

决定必须来自当前分配人的 Web/Android/微信/抖音本人认证连接。Agent 不代人审批，TG 首发仅提供登录门户链接。需同时检查步骤版本、申请版本、准确快照及审批权限；按规则再核对最近 MFA。退回和拒绝必须有原因。

同一步骤最多一项最终决定，数据库唯一约束兜底。两个设备同时决策最多一个成功；同幂等键双击返回原结果。授权必须在幂等重放之前再次检查。批准当前步骤后只激活下一步；最后一步批准才把申请 approved。

退回/拒绝/撤回会取消剩余未执行步骤，保留已经执行的决定。撤回仅申请本人且固定制度允许时执行；已批准不能简单撤回。审批人停用、权限变化、附件不可用或制度要求的身份验证缺失要显示明确阻断，不自动同意、不跳步、不假冒下一人决定。

每步指定身份及其授权依据固定记录。后续角色变化不能悄悄更换原审批责任；确需调整首版流程时由申请人按制度撤回、重新送审。复杂转交、代理、加签、会签不伪装成现有顺序步骤已支持。

## 5. 各业务后续事实

| 业务 | 批准后的独立动作 | 防止状态混用 |
| --- | --- | --- |
| 合同 | 待签署、登记签署日期与固定签署件、达到生效日期、履约节点、完成/终止 | 新补充协议生效前保持旧有效修订；应收不计费用 |
| 采购 | 按批准修订下多张订单、分行分批验收、反向退货、差异重审、结算核对 | 合格净数量不得超规则；取消不抹去已交付或付款 |
| 报销 | 票据核验、重复候选解释、关联唯一实际费用、人工付款及分配 | approved 仍可 unsettled；公司已付与员工报销避免双付 |
| 项目变更 | 固定基线影响、审批、实施新预算/计划修订、核验执行 | 获批与已实施分别表达，不改写旧基线 |

合同正文、审批件、签署件分别绑定准确文件版本。已批准关键内容不可覆盖；补充协议/变更需新业务修订并重审。采购验收和付款、报销费用和付款使用独立追加记录及冲销引用，不允许直接改历史累计数。

## 6. 引用、可见性与页面

业务修订及申请快照在同一事务向 [统一版本引用](20-retention-and-reference-protection.md) 登记附件。引用释放由各业务生命周期核对后追加，不给审批页面通用“解除文件保护”按钮。文件不可读时不返回隐藏文件标题、对象路径或云凭据。

申请人、审批分配人和管理角色分别受真实对象权限约束；系统配置管理员不自动读取业务内容。列表先按权限和实际分配过滤，再分页。审批工作台以数据库 active 步骤为事实来源，提醒仅面向实际待办人，推送丢失不改变任务状态。

页面遵守现有 CopyPaste 设计：业务修订与当前审批快照可辨、批准和结算分开、金额带币种、日期带明确业务时区；冲突保留表单；状态/风险使用语义色，确认操作有准确主体、内容与版本。小程序不承接120GB上传，附件仅通过固定下载授权读取。

## 7. 必须提供的验证

覆盖完整顺序批准、金额边界/规则缺失/规则重叠、本人审批默认拒绝、审批人停用、附件失权/版本错绑、审核中编辑拒绝、旧版本冲突、退回重提生成新实例、拒绝终态、允许/禁止撤回、双设备决策、幂等重放前撤权，以及审计失败的原子回滚。

各业务另提供签署与生效日期、补充协议不覆盖旧有效版、分批验收与退货、超收/订单差异、批准未付款、多费用关联去重、部分支付/退款与并发分配等场景。真实外部签名、银行付款或通知消息不属于本地隔离测试证据，首版系统也不直接执行银行支付。
