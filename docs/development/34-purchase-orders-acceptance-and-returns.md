# 采购订单、分批验收与来源退货

日期：2026-10-24；范围：迁移0035、Go接口与Web实际操作。遵循[采购与OA需求](../requirements/04-workflows-and-oa.md)、[财务口径](../requirements/05-finance-and-subscriptions.md)及[商业草稿与审批](33-purchase-and-claim-approval-drafts.md)。首发四端与完整财务目标继续保留，本文记录本次履行环节。

## 1. 业务边界

采购申请先固定商业修订，再通过既有顺序审批。批准依据继续不可变；后续订单、验收、拒收、退货、取消余量均追加独立事实，以采购头版本串联。

员工通过本模块人工登记实际订单及交付事实，核对真实单据、数量、日期和取消依据。系统不向供应商发出订单、确认外部取消或执行银行付款。订单金额、审批额度占用、净验收数量、实际费用和现金流分别解释，禁止互相充当凭证。

已实现：同一批准采购对应多张订单、按行分批验收/拒收、按准确验收来源退货、取消未交付余量、结束采购后续履行、当前权限下的固定证据和有界历史。

仍待完成：明确制度下的价格/供应商/金额差异审批、例外超收、订单更正及更完整的履行修订、付款/退款、差异和结算核查、采购完成条件、Taro三端履行录入和平台真机验证。本轮严格额度内登记不代表上述完整闭环已经交付。

唯一实际费用、分摊、人工确认/全额冲销和发生支出报表已后续接入，见[费用实施协议](35-canonical-actual-costs-and-incurred-reports.md)。采购/报销/生效合同可关联同一费用；这不使验收自动成为费用或结算证据。

## 2. 准入与职责

新增独立 `purchase_operator` 角色，包含 `purchase.read`、`purchase.execute`，要求MFA。迁移与组织初始化仅建立角色，不向员工自动授权。采购管理人负责草稿，审批处理人负责被指派步骤；两者均不自动获得履行登记能力。

全部写入要求当前采购读取/履行权限、有效人工会话、数据库记录的最近10分钟MFA、当前项目可写。允许交互渠道为Web、Android、微信、抖音；带Agent运行身份或其他渠道不得登记。本轮只有Web提供对应界面，后端准入不等于移动产品已经完成。

每个写入携带 `expected_version`、准确 `revision_id`、`content_hash` 和1至200字登记依据。当前头须仍绑定同一已批准商业修订、申请及摘要。订单同时固定准确批准申请修订；供应商当前资料更新不会替换批准资料。

查阅要求当前父采购的 `purchase.read`。供应商姓名、附件详情另查当前权限、范围和可用性，失权时不展示对应名称或下载入口。系统管理员没有自动业务读取权。游标绑定组织、员工、授权版本、渠道、运行、采购、列表类型和订单筛选。

## 3. 订单与准确金额

订单包含准确批准供应商/资料修订、真实外部编号、实际订购日、预计交付日、1至100行、1至20个不同正式证据版本及备注。订购日不得晚于香港当前日期；交付日不得早于订购日。同组织和供应商下的外部编号按数据库小写规范化后唯一，避免换大小写重复登记。

每行引用一条批准采购行，描述和单位由服务器复制。数量为正十进制字符串、最多6位小数；单价必须与准确批准单价相同。税额和折扣遵循币种精度。数量乘单价以整数精确计算，按批准规则只舍入一次，再按原含税方式计算行额；合计由服务器生成。

同一批准行的累计有效数量、金额、税额和折扣均不得超过批准范围。不同单价，包括更低价格，当前均返回明确的差异审批错误；没有默认容差、自动授权阈值或员工可绕过的例外开关。独立差异制度完成前，界面保留输入并说明原因。

附件通过当前业务证据校验并固定正式版本，后续更新不改绑；保留引用登记为 `purchase_order`，原商业依据仍为 `purchase_revision`。保留评估Schema同步支持这些类别，不能因新增引用使评估响应不合法。

## 4. 分批验收、拒收与退货

每批只属于一张准确订单，包含实际日期、1至100行、1至20个固定证据版本、备注及登记依据。每行记录订单行、正数量、结果及1至2000字结果依据。

| 结果 | 数量处理 | 后续行为 |
| --- | --- | --- |
| accepted：通过验收 | 增加净验收数量 | 可作为准确退货来源 |
| rejected：拒收 | 保留本批事实，不增加净验收 | 可另行登记补送验收 |
| returned：退货 | 减少净验收数量 | 必须冲回一条既有accepted明细 |

收货批次中的通过与拒收合计不得超过该行本批登记前的待收数量。拒收补送、退货重新交付可能增加历史累计到货量；净验收数量始终在0至订单数量之间。这不构成例外超收授权。

退货与新到货分别登记。退货引用同订单、同订单行、更早登记的通过明细；实际日期不得早于订单和原验收日，也不得晚于香港当前日期。拒收、其他订单或既有退货不能作为来源。同一来源的累计退货不得超过原通过数量，接口返回其当前可退数量；原明细不更新或删除。

验收齐全使订单显示“净验收齐全”，采购继续处于验收阶段。实际费用、差异与结算尚未核查时，不提供“采购已完成”结果。

## 5. 取消与额度释放

只有仍有待收数量的订单可登记余量取消，同单取消记录唯一。原始数量、金额、日期和证据继续保留；之后禁止新增通过/拒收，既有通过来源仍可退货。

| 情况 | 数量占用 | 金额/税额/折扣占用 |
| --- | --- | --- |
| 有效订单 | 原始订购数量 | 原始对应金额 |
| 余量已取消，或父采购已取消 | 当前净验收数量 | 原始对应金额 × 净验收数量 ÷ 原始订购数量，向上取整至币种精度 |

各项分别向上取整，避免拆单舍入扩大批准额度。这是保守的审批额度预留估计，不能当作会计确认、发票、付款或退款金额。例：3件共0.01 HKD，验收1件后取消余量，占用仍为0.01 HKD；如再订2件需另0.01 HKD，会被阻断，等待真实差异处理。历史原始订单金额不变。

结束采购后续履行前，有效订单须净验收齐全或已取消余量。采购进入 `cancelled` 后不再订购/收货，仍可追加原来源退货，生命周期保持取消。原已验收齐全订单后续退货时，父采购取消同时关闭其后续承诺，不重新生成待收任务。

取消不删除批准、订单、验收、引用或审计，也不声称供应商已退款。已有费用和支付的后续处理仍由财务模块完成。

## 6. 状态、数据与数据库约束

| 事实 | 采购生命周期 | 审批状态 |
| --- | --- | --- |
| 已批准，尚无履行记录 | requested | approved |
| 已登记订单，尚无验收历史 | ordering | approved |
| 已有验收/拒收/退货历史 | receiving | approved |
| 已登记采购取消，含后续来源退货 | cancelled | approved |

非批准采购、报销及原审批仍遵守原协议。商业修订不因履行增加改变；采购头每次推进版本，履行另有连续序号。取消全部订单不会抹去已有订购或验收历史。

新增五张不可变事实表：`purchase_orders`、`purchase_order_lines`、`purchase_receipts`、`purchase_receipt_lines`、`purchase_execution_events`。外键绑定组织、采购、订单、行、准确商业/申请修订及退货来源。延期约束核验头与最新事件版本/阶段、完整序列、事件准确对象、头行数量/金额、独立SQL复算、累计额度、逐批待收、来源可退量和取消顺序。

项目锁在采购锁之前，取得采购锁后重读版本与权限。依据固定、事实插入、头推进、不可变审计、Outbox、幂等结果同事务提交。两端同一基础版本只能一项成功，失败不会留下半张订单或验收。数据库独立拒绝越额订单、重用旧订单冒充新事件、无事实头跳转和记录重写。

幂等重放前重新验证当前权限和数据库MFA，不再次新增事实。旧采购结果按当前证据权限重新投影；基础版本过时则关闭其中的写入能力，客户端读取最新履行资料。

## 7. 已实现接口

均位于 `/v1/purchases/{id}` 下，精确DTO由同源[OpenAPI](openapi.json)定义。

| 方法与后缀 | DTO/行为 |
| --- | --- |
| GET /fulfillment | `PurchaseFulfillment`；批准行级额度/净验收/有效待收及计数 |
| GET /orders | `PurchaseOrder`分页 |
| GET /orders/{order} | 固定原始订单及当前净验收/承诺状态 |
| POST /orders | `PurchaseOrderCreate`；追加订单，201返回更新后的`Spend`头 |
| POST /orders/{order}/cancel | `PurchaseExecutionInput`；取消余量，返回更新后的`Spend`头 |
| GET /receipts | `PurchaseReceipt`分页；可按order_id筛选 |
| GET /receipts/{receipt} | 准确批次及来源当前可退数量 |
| POST /receipts | `PurchaseReceiptCreate`；追加验收或退货，201返回更新后的`Spend`头 |
| GET /execution-events | 连续履行事件分页，不输出会话ID或MFA凭证 |
| POST /cancel | `PurchaseExecutionInput`；取消后续履行，返回更新后的`Spend`头 |

列表默认20、上限100，禁止一次拉取全部历史。写入返回采购头以更新CAS版本，准确订单/验收由对应有权详情或分页读取。通用 `/transition`、费用和差异路线仍有规划定义，不能据此认定已经实现。
