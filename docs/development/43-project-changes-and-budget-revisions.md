# 项目范围变更、预算修订与明确实施

日期：2026-10-24。状态：本地Web/API和移动审批快照已实现，完整后端回归、Web及两端编译检查通过；完整原生业务仍待验收。关联PM-03/05/08/11及WP-04，承接[项目需求](../requirements/03-projects-and-knowledge.md)、[申请与顺序审批](24-request-snapshots-and-sequential-approvals.md)和[实际费用](35-canonical-actual-costs-and-incurred-reports.md)。代码位于app/，说明和证据位于docs/，不调用本地虚拟化。

## 1. 准确提案

每次变更保存不可变修订：标题、审批类别、影响说明、拟实施的完整范围和起止日期、审批币种、可选完整预算行及准确正式文件版本。基线固定当时项目版本、名称、范围、日期、分类，以及该币种当前已启用预算的ID和全部行。预算按币种独立修订，每行包含类别、期间起止和非负原币金额；同一类别期间不得重叠，各币种不折算合并。

`budget_lines=null`表示预算不变，空数组表示明确将该币种预算调整为空；两者不能互换。预算修订为该币种完整替换，其他币种保持各自历史。审批金额为逐个类别／期间正向增加的合计，减少不能抵消另一个类别的增加；净变动和拟预算总额分别展示。纯范围／日期变更也要明确选择用于匹配制度的币种，审批金额为0，不假设组织默认币种。

每次包含预算的草稿修订生成独立draft预算及固定行，不覆盖旧草稿；批准提案仍不改变项目或启用预算。实施时原币旧预算变为superseded，新预算变为approved，全部旧修订保留。实际费用、付款、采购订单和合同不随预算修改，也不会由预算自动生成。

同一个变更的币种在创建后固定；修订不能改为另一币种。另一币种的调整须建立另一份提案，重新选用该币种的基线和制度。项目版本是保守并发边界：即使仅改预算，实施也增加项目版本，使其他基于旧项目版本的提案明确失效。

## 2. 审批与实施

项目变更接入既有change类别的通用申请、制度预览、准确快照、顺序人工决定、退回／撤回和历史。草稿修改产生新业务修订，已有可编辑申请须明确刷新；审批中及已批准提案不可编辑。旧基线可读但不能送审或实施；项目版本变化后必须重新起草并重新批准，不能自动换基线继承旧批准。

批准后由有权人员在真实交互会话、近期MFA下明确实施，固定变更版本／修订／指纹、准确项目基础版本及已批准申请修订。逐项确认范围／日期和预算影响，填写实施依据；验证成功不自动实施，AI／TG不得代替本人操作。项目处于closing／archived／cancelled时拒绝普通写入。已激活或暂停项目的范围／日期调整走此流程，草稿项目仍可直接完善基础资料。

事务依次锁组织授权、用户、项目、变更、申请及固定文件；实施事实、范围／日期／项目版本、新旧预算状态、变更阶段、审计、outbox和幂等收据同事务提交。并发实施最多一次，审计失败全部回滚。幂等重放前仍核对当前业务／预算／文件权限和真实会话。数据库独立检查批准来源、准确基线、人工会话和历史不可变性。

## 3. 权限、页面与验证门槛

变更沿用change.read/create/submit/implement，补充change.update和budget.read；实施要求project.update。需要读取固定旧预算及提案的人员必须拥有预算权限，不能只凭变更阅读权披露金额。专用实施角色要求MFA且默认不绑定，管理员本身不获得业务资料权限。旧无来源记录保留旧协议，不编造审批或预算历史。

Web提供项目变更与预算页签、准确前后对照、预算修订／历史、共用申请入口和明确实施表单。冲突或失去写权限但仍可读时保留输入并禁止再次提交旧依据；失去阅读权限或历史读取失败时移除相应缓存及详情。沿用官网暖白／蓝灰黑、墨色主操作及品牌蓝来源，双主题及五档宽度核对长标题、日期、金额和固定版本。

验证覆盖首次预算、范围／日期变更、退回重提、批准未实施、多币种独立、类别增加不可净额抵消、不可变历史、旧项目基线、并发唯一实施、真实MFA／自动身份、文件与预算撤权、只读项目、审计整体回滚、直接SQL反例及有效控制。完整项目财务结项、移动业务和真实云／120GB仍按原首发门禁执行，不能以本页计划充当通过证据。

## 4. 数据和数值约束

| 对象 | 固定内容与约束 |
| --- | --- |
| change_requests | 兼容旧表；新协议为1，固定项目、创建人、分类和币种；保存当前修订、已批准修订、关联申请及乐观版本 |
| project_change_revisions | 不可变完整提案、完整项目／该币种预算基线、前序修订、序号、作者、原因、内容指纹、审批增加合计、预算净变化及目标草稿预算 |
| project_change_files | 有序固定正式文件版本；受引用保护，原文件有新版本不改变旧提案附件 |
| project_budgets / budget_lines | 每次提案的独立预算及有序明细；同项目同币种最多一份已实施预算；旧行不能重写或删除 |
| project_change_implementations | 不可变人工事实，固定实际用户／会话、变更及申请修订、指纹、实施前后项目版本、两项核实与原因 |
| requests / request_revisions | 沿用通用独立审批，固定业务修订、完整内容与基线、净变化、审批增加合计及相同顺序的正式文件版本 |

预算行最多100项，每项包含 `category`、`period_start`、`period_end`、`amount`。期间按含首尾日期判断，同类别的重叠期间拒绝；不同类别可在相同期间分配预算。金额为十进制字符串，按组织已配置币种的精度核对，不经过浮点换算。缺字段、类型不符与超额精度拒绝，不能静默填默认金额。

审批增加合计由 `(类别,期间开始,期间结束)` 匹配前后行，累加每项正差额；原设备100降至60、另增服务40时，净变化为0，审批增加合计仍为40。期间改变按旧行减少、新行增加计算。后端与数据库分别核对数值；前端只展示服务端固定的数值和准确口径。

草稿可暂不选文件，准备送审要求1—20项可读且可用的正式版本；内容引用、当前文件头与固定版本各自核对。对 `budget_lines` 的省略不等于 `null`，`start_date`／`due_date` 的显式 `null` 代表完整提案中的未设置值。接口具体必需字段以[OpenAPI](openapi.json)为准。

## 5. 接口与客户端提交

以下路径统一加 `/v1`，命令沿用已认证会话、CSRF和幂等键。列表使用与当前权限绑定的游标；变更、预算和审批任务在分页前完成业务／预算权限过滤。

| 方法与路径 | 输入及结果 |
| --- | --- |
| GET /projects/{id}/change-basis?currency=HKD | 读取指定币种的准确当前项目／预算基线；币种必须已配置 |
| GET /projects/{id}/changes | 可读新协议变更列表，支持关键词、状态与游标 |
| POST /projects/{id}/changes | 完整content、base_project_version、可空base_budget_id和原因；返回ChangeReceipt |
| GET /changes/{id} | 当前完整修订、实施事实与当前can_edit／can_prepare／can_implement能力 |
| PATCH /changes/{id} | 增加expected_version、base_revision_id并提交完整新提案；生成新修订，不覆盖旧内容 |
| GET /changes/{id}/revisions | 有序固定修订及分页 |
| GET /changes/{id}/revisions/{revision} | 读取该变更的准确固定历史 |
| POST /changes/{id}/submit | expected_version、revision_id、content_hash、reason；准备申请草稿并返回Request，尚未正式送审 |
| POST /changes/{id}/implement | 准确变更版本／修订／指纹、request_revision_id、base_project_version、scope_verified、budget_verified及原因；返回ChangeReceipt |
| GET /projects/{id}/budgets | 按currency和state筛选，state为draft／approved／superseded；草稿另要求来源变更阅读权 |

变更的 `submit` 保留既有路径，但含义明确为准备申请；之后仍须使用通用申请的预览／正式送审流程，不能由客户端将草稿直接标为已送审。申请快照的 `project_change_basis` 与 `project_change_budget_delta` 为服务端固定值。审批通过返回业务详情，保留「已批准，尚未实施」提示。

客户端首次读取基线后必须明确固定；修改提案不自动刷新基线。成功实施后失效项目、变更、预算、基线与关联申请查询；409或写权限变化时重新读取当前事实，在仍有阅读权限的前提下保留用户输入、两项人工声明和原固定依据，禁止重发旧操作。任何失去阅读权限的查询不得继续显示旧缓存或敏感详情。

## 6. 数据库与历史保护

迁移0045在写入时独立验证完整提案及指纹、基线、预算行、相同顺序的固定文件、申请快照，以及正式批准的准确来源。延迟约束在事务结束前核对业务头、修订、文件和申请的一致性。实施前锁定实际数据库会话，核对交互设备类型、当前用户授权版本、未撤销／未过期会话和十分钟内真实MFA，不接受客户端伪造的时间或自动身份声明。

实施触发器在同一事务内启用目标预算、替代前任预算、更新项目和业务阶段；应用审计或outbox失败时整体回滚。活动项目的普通范围／日期SQL修改也受独立保护。应用角色只可读取和插入固定历史，不可更新／删除修订、文件、实施或预算行；不能删除变更及预算头。旧协议数据保持旧协议，不捏造历史。

## 7. 页面和原生端边界

Web提供项目「变更」「预算」页签、完整前后对照、按币种的预算历史、正式文件选择、准备申请、独立审批和明确实施。实施前两项核实初始不选，MFA完成本身不提交操作。预算编辑使用稳定行标识；添加聚焦新行，移除聚焦相邻行，移除最后一行回到添加入口，并保留其余输入。

移动端通用审批详情支持相同的完整项目／预算固定快照和来源文件，审批结果沿用原申请流程。完整移动变更创建、预算管理、明确实施和Android原生宿主尚需独立推进；微信／抖音编译或H5运行不能作为这些能力已完成的证明。
