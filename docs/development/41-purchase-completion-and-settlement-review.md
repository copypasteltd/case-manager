# 采购完成与结算核对

日期：2026-10-24。状态：已实现并通过本地原生PG、完整后端及Web验证；完整四端与真实环境另行验收。依据OA-10及[采购履行](34-purchase-orders-acceptance-and-returns.md)、[差异执行基线](40-purchase-variance-approval-and-execution-baselines.md)。目标是完成订单、交付、差异处理与结算的明确人工核对，并保留不可变完成事实。

## 1. 完成条件

完成须使用准确原商业批准、当前采购版本及完整核对指纹。至少已有实际合格验收；所有未取消订单必须净验收完整，取消余量继续保留已经交付部分；尚在审批的差异申请先完成处理。未使用额度、取消余量、价格／费用差异和未启用提案都在固定集合内逐项展示，存在这些情形时必须说明处置，不能自动删除或视为新批准。

全部关联实际费用、付款分配、退款家族及差异提案均按当前权限核对。无法完整读取时返回受限状态，不输出部分金额／数量或将其当作零。确认费用必须足额有效结算，未处理退款不能被完成操作掩盖。批准金额、订单承诺、净验收、真实费用和资金结算各自保留口径。

经办人明确选择“按已归集实际费用核对”或“经核实无应付义务”。前者要求存在已确认实际费用；后者要求不存在有效实际费用或有效付款分配，并填写核实说明。无应付义务不是系统从空列表推断的结果；非零订单承诺仍须单独说明差异并提供准确凭证。任何选择均不能绕过已存在的未结费用。

## 2. 人工登记和历史

使用独立默认未绑定的`purchase_completer`角色，要求真实人工会话、近期MFA、准确文件版本、实际日期、交付核实、费用归集核实和差异核实声明。声明初始均未选中；AI／TG自动身份不得登记。无实际支付时不能用本操作生成付款、费用或结算事实。

`purchase_completions`保存准确批准修订、完成时采购版本、当时订单／验收／执行基线／差异／费用／资金集合、指纹、核实说明、处置、日期和会话。完成推进采购生命周期为`completed`并追加履行事件，审计、幂等和引用保护同事务提交。

完成后禁止新订单、普通新验收、取消和启用／编辑差异。既有合格验收的真实来源退货仍可单独登记，保持完成事实及完成日期；后续退货、费用更正或退款改变当前依据时，页面明确显示“完成时依据已变化”，分别处理后续义务，不自动重写历史或宣称今天仍无未结事项。

## 3. 接口与事务

新增`GET /v1/purchases/{id}/completion-preview`、`GET /v1/purchases/{id}/completion`和`POST /v1/purchases/{id}/completion`。精确字段以同源OpenAPI为准。预览使用一致读快照并重新核对授权；受限预览不返回核对集合或指纹。

| 操作 | 输入／输出约束 |
| --- | --- |
| 完成预览 | 返回采购版本、`visibility`、完整固定集合、指纹、待处理原因、差异标志、允许核实方式和`can_complete`。受限时集合／指纹为`null`、方式为空；未批准时明确`not_approved` |
| 人工登记 | 要求原批准修订／SHA-256、当前版本、准确集合指纹、实际日期、三项声明、核实方式、说明、差异处置、原因与1—20个正式版本 |
| 登记回执 | 仅返回采购ID、新采购版本、完成ID；重放之前仍须重新检查现有权限、完整资料和实际会话 |
| 完成历史 | 返回当时完整集合、原说明和准确凭证，并用`basis_state=current/changed`说明与当下依据是否一致；不回写旧集合 |

核对集合使用数据库规范化JSON及其MD5作为并发变化标识；它不是文件完整性或密码安全承诺，文件和商业正文继续使用各自既有SHA-256协议。快照涵盖完整订单／验收／来源退货、每条差异的版本与状态、关联费用及冲销、付款／退款家族和全部分配。付款关联的其他费用与合同也按既有资金读取规则检查，不能通过共同付款绕过其他项目权限。

单次核对上限为1000张订单、5000批验收／退货、1000条费用、1000条资金和1000份差异提案。集合超限直接阻断人工登记并要求范围评审，不将隐藏尾页当作完整依据。原币不一致属于阻断事项，页面不自动换算或合并不同币种。

写入先核对当前权限和实际会话，再按相关项目、父采购、相关费用、资金ID顺序加锁，重验完整关联集合及指纹。外部下单、退货、启用差异、费用冲销、付款／退款／分配变化都使旧依据拒绝，保留用户输入；不自动刷新依据后提交。幂等重放同样先重验当前权限和实际会话。

迁移0042独立增加完成表／引用、不可变约束、头与事件一致性及当前依据／会话校验，扩展现有履行时间顺序保护；不改写已应用迁移。数据库独立拒绝伪造完成、未结余额、缺失凭证、未核实声明及完成后新履行。

追加迁移0043补齐未使用金额的独立判断：当前执行总额与所有有效订单占用金额不相等，也须填写差异处置。数量已全部验收、旧订单及费用均已结清时仍可能有未用金额，例如独立启用后的额度HKD30而旧订单及实际费用均为HKD20。该判断只约束新的完成登记，不改写0042迁移或已存的历史集合。

## 4. 页面与验证要求

Web采购详情展示完成核对、明确登记、完成时集合和当下依据变化。继续使用官网双主题、墨色主操作、品牌蓝来源链接及既有语义状态。受限权限显示未知，长核对表可滚动，冲突保留全部说明并将焦点留在对话框内。

具体信息层级、折叠分组、默认未选声明、凭证选择、来源退货和受限分支见[采购完成页面设计](../design/14-purchase-completion-and-settlement-review.md)。表单打开时独立保存准确采购和预览对象，后续后台刷新失败不能卸载已填写表单或覆盖固定依据。

原生PG须验证交付／结算阻断、明确无应付、取消余量、未启用差异、准确指纹、并发、审计回滚、真实MFA／自动身份、撤权、不可变历史、来源退货和SQL反例。浏览器须验证完整实际操作、冲突、只读未知及双主题五档宽度。完成验证前不将此计划写为验收证据；真实采购／银行／云、平台真机和完整移动采购另行验收。

## 5. 实现位置与复验命令

后端在`app/backend/internal/spend/completion_*.go`及采购履行／差异的现有服务内实现；HTTP入口为`app/backend/internal/httpapi/purchase_completion.go`，独立PG场景为同目录`purchase_completion_integration_test.go`。Web采购详情接入`app/web/src/PurchaseCompletion.tsx`，履行区保留已完成采购的准确来源退货入口。同源契约由`app/scripts/build_openapi.py`生成文档JSON与嵌入JSON，再生成共享TypeScript类型；当前共218路径、278操作、449项Schema。
