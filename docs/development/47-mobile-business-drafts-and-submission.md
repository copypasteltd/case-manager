# 移动业务草稿与明确送审

日期：2026-10-24。适用代码为 `app/mobile/` 的 Taro 公共客户端。本文补齐合同、采购、报销从业务起草到申请送审的客户端协议；首发范围仍以[各端能力矩阵](06-clients-and-pages.md)为准。

## 1. 业务入口与完成含义

工作台按当前权限提供合同、采购、报销入口。三个列表使用真实分页及名称查找；创建入口检查相应 `*.create`，已有业务的编辑、准备申请分别使用服务器的 `can_edit`、`can_prepare_request`。前端权限控制只用于呈现，服务器继续检查每次访问、命令及幂等重放。

`pages/business/index` 是第九个公共页面，参数仅接受 contract、purchase、claim 三类及合法资源 UUID。创建和编辑共用长表单，当前业务查阅沿用实际内容与固定版本呈现。项目、分类及主合同归属仅在创建时选择，PATCH 不改变业务范围。

| 用户动作 | 实际结果 | 后续动作 |
| --- | --- | --- |
| 保存业务草稿 | POST 创建，或 PATCH 追加业务内容修订 | 读取实际保存结果与服务器计算金额 |
| 建立申请草稿 | 固定业务 ID、版本、修订、内容摘要 | 尚未分配审批步骤 |
| 更新申请草稿 | 明确采用当前业务修订，追加申请修订 | 旧快照与旧决定继续保留 |
| 核对并送审 | 先 GET 完整预览，人工核对后 POST submit | 按预览中的制度和人员执行 |
| 撤回申请 | 按固定制度取消未完成步骤 | 保留既有决定；后续须重新核对 |

商业批准不能自动生成签署、生效、订单、验收、费用入账或实际付款。复杂履行业务继续由各自协议约束。

## 2. 三类完整输入

合同支持标题、类别、项目/分类、负责人、主合同、收付方向、合同类型、原币总额及其中税额、起止日期、固定往来方修订、固定正文版本、收付款节点、续约/终止条款及说明。计划支持未整理、按节点收付、明确无收付义务；后者必须填写依据。节点最多100项，保留稳定 UUID，不按数组序号重新生成身份。

采购支持用途、负责人、计价/舍入规则、交付日期、预算文字依据、最多20个候选供应商修订、20个报价版本及100行明细。每行保留描述、数量、单位、精确单价、税额及折扣。客户端不自行计算批准金额。

报销支持费用期间、含税计价、舍入规则及100行费用；每行保留实际费用、日期、类别、员工垫付/公司已付、供应商修订、最多20个固定凭证版本、缺失凭证及重复凭证说明。费用合计与其中员工垫付分别呈现，不能把公司已付费用再次计为应付员工。

明细和节点使用稳定身份；在手机中逐行展开编辑，其他行的输入保留，不同时展开100个复杂表单。删除明细同时移除该行的暂存引用，重排不会把凭证或供应商换到其他行。

## 3. 选择器与固定依据

人员从当前有权读取的真实成员中选择，另提供本人及暂不指定。项目从真实列表选择。往来方和文件候选可在本项目、公司公共范围间切换，支持查找和继续分页；候选资料分类不得高于业务分类。重新选择往来方固定所选当前修订，文件选择进入版本列表后固定准确正式版本。

仅当前可用、扫描通过或已有正式扫描例外的文件版本可选。例外必须显示风险提示。每项文件依据显示版本序号和完整 SHA-256；保存时服务器再次核查范围、权限、可用性和扫描状态，当前列表不是授权保证。

改变创建范围或分类会清除已选往来方和文件。编辑时若服务器返回原引用 ID、却不能完整提供引用资料，客户端停止保存，避免通过重建表单静默清空引用。用户可刷新，或明确点击「清除当前全部往来方与文件引用」再重新选择。查阅页面继续保留真实引用 ID 的事实，不把失去阅读权解释为从未引用。

普通附件/拍照上传仍须按原首发矩阵补齐；本页选择已有正式版本不能替代小程序本机附件上传能力。

## 4. 精度、日期与错误

金额、数量、单价始终作为十进制字符串传输。未知值传 null；不使用 Number/浮点合计、不在客户端四舍五入、不将空白默认为0。服务器按币种精度、计价基础与舍入规则计算，保存后再显示实际结果。数量最多6位小数且非空时须大于0；其他金额的基本格式为非负十进制数，不接受科学计数法。

日期按 YYYY-MM-DD 输入和保存，不通过设备时区改写。客户端检查日历存在性和明确的日期顺序；业务完整性、金额关系、币种目录、重复凭证等仍由服务器核对。

客户端错误显示顶部摘要及字段下说明，摘要可定位对应输入；验证失败不发命令。服务器400/422只提取有界的 `field` 和 `safe_message`，不携带额外内部响应内容。已知字段定位到实际输入或分段；未指定具体行的服务器错误定位到明细段，不能猜测为某一行。具体平台焦点/读屏行为须分别真机验证。

H5通过明确的字符串 `aria-invalid="true"/"false"` 和关联错误说明标记字段，不能把布尔属性序列化为空字符串。原生端使用本平台的名称与焦点属性，仍需独立读屏检查。

## 5. 草稿、身份与容量

业务输入加入原有 `MemoryDrafts`，与任务/审批/交付草稿共用15分钟、最多32项和合计10万字符的预算。恢复绑定当前登录代次、本人、服务器授权版本及准确业务版本；旧授权不能将缓存回退。只按明确字段白名单深复制文字、原币字符串、稳定行身份和基本选择 ID。

固定文件、往来方修订、文件选择、人工声明、MFA、密码和凭据不进入可编辑草稿缓存。页面隐藏使当前读取和子组件结束；再次显示先读取当前权限和业务资料，再恢复匹配的文字。已保存业务的原有依据来自本次服务器读取，不能与尚未保存的本机选择混淆。

超出共享容量时不截断文字；当前页面继续编辑，并明确提示这次输入未进入恢复缓存，应先保存再离开。退出和完整重载清空本机会话输入。后端已经保存的业务草稿不受本机缓存寿命影响。

## 6. 命令结果与并发

新业务使用原生会话的公开随机 request nonce 和计数器派生稳定行身份；不能使用 access/refresh token 派生操作键。保存以完整表单体、准确业务版本/修订及独立幂等键执行，不自动重放写请求。

此前命令记录的10万字符容量不足以容纳合法100行长表单。现将全会话命令签名及绑定总容量设为4Mi字符，最多128项；未核对记录不淘汰。单次请求体仍预先按 UTF-8 字节核对后端1MiB上限，超限不发送。这与可编辑输入的10万字符预算是两种不同用途的界限。

`platform/encoding.ts` 以可移植UTF-8实现计数和公开意图编码，不依赖小程序未必提供的浏览器 `TextEncoder` 全局对象。中文、补充平面字符、孤立UTF-16代理项按标准替换字符处理；大小限制按真实线缆字节而非JavaScript字符串长度。

网络中断、会话变化或不完整成功回执均视为结果待核对。当前表单保留输入并停止提交；返回后不自动写入。用户明确用相同输入核对时复用原键，不能把同一未知结果改写成另一次创建。收到成功结果后先核对对象身份、类型、版本及摘要，再清理当前输入。页面更新失败不能把已收到的业务成功错误地降为可随意另建。

新业务与申请回执分别检查类型、准确对象、递增版本及固定修订；准备／更新／送审／撤回额外检查目标业务、预期申请状态和对应修订依据。不完整、旧对象或错误状态的HTTP成功不能清除输入或被记为已经完成。

编辑携带 `expected_version` 和 `base_revision_id`。真实409/412、失权和结果未知保留本机内容、停止旧提交；刷新须重新核对新基础版。跨完整进程重载的统一操作查询/恢复中心仍待实现，不能把第二次新建当作结果确认。

## 7. 申请预览、人工确认与历史

准备申请绑定准确业务 ID/版本/修订/摘要。更新申请先读取当前业务并完整呈现，用户明确核对后才追加申请修订。

送审由用户打开预览后取得 `SubmissionPreview`，核对 request_id、request_version、revision_id 与 content_hash 均匹配当前申请。完整展示固定内容、原币金额、附件、制度修订、步骤、指定人员、自审政策和撤回规则。人工核对框初始未勾选，不从查阅动作、页面返回或历史草稿恢复。POST 同时固定制度 ID 和 preview_hash，不能在旧预览上自动采用新制度重试。

送审成功后，服务器追加包含制度及审批授权证据的新申请修订，业务内容仍固定原业务修订。客户端检查新申请修订及递增版本，不能错误要求申请修订ID保持不变。更新申请同样追加修订；撤回仅记录对当前修订的撤回及步骤取消，不能伪造新的业务内容。

撤回需要原因与明确确认。申请历史分页读取，每项按原修订展示完整固定内容、当时制度及决定，明确标记为历史；不把旧审批通过展示成当前修订已通过。
