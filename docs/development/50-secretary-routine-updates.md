# 秘书常规项目与任务更新实现

## 2. 员工操作与业务约束

进入对应项目的私密或项目共享会话，选择“更新项目”任务，再选择“准确业务更新”。页面读取真实项目／任务及当前版本，展示当前值。员工选字段或动作，填写新值和原因；日期可明确清空，未选字段不进入请求。选择和预览不会发送请求，也不会修改业务记录。

发送前显示本次准确更新。员工可以移除或修改选择，最终随消息确认发送。服务端以实际发起人身份重新核对项目范围、共同成员的阅读／AI 许可、写入权限和基础版本。普通聊天可以整理建议，但不能据此调用写工具；缺少准确范围时返回待补资料。

页面的“任务当前进展”显示原值、目标值、基础版本、结果版本及真实业务操作号。`authorized` 只表示此次固定范围，运行状态仍可能是排队、失败、取消或待补充；只有真实提交产生 `committed`。运行成功回复也通过业务结果字段区分是否完成事项。

禁止通过本入口修改项目成员、负责人、资料分类、权限或降低任务人工验收要求。需要人工验收的任务不能由秘书代为完成，即使发起人同时拥有验收权限。归档只读、依赖未完、子任务未完及项目变更审批要求由原业务服务核对，不复制一套较宽松的 AI 规则。

## 3. HTTP 输入与回执

沿用 `POST /v1/conversations/{id}/runs`，增加可选 `mutation`；普通请求保持原语义。示例：

```json
{
  "expected_version": 1,
  "context_security_version": 1,
  "profile_id": "已安装且获准使用的项目更新配置 UUID",
  "client_message_id": "本次明确发送的 UUID",
  "message": "按选定内容更正任务标题。",
  "mutation": {
    "tool": "update_task",
    "arguments": {
      "id": "本项目内准确任务 UUID",
      "expected_version": 7,
      "title": "核对客户反馈并整理修订清单",
      "reason": "根据已确认的工作内容更正标题"
    }
  }
}
```

UUID 文本为示意，上线调用必须使用真实标识。不能提交执行身份、任意会话授权、旧 run 授权或额外工具。`reason` 必须为 1—200 字；更新参数最多 64 KiB，固定意图含原值最多 100000 字节。原业务字段、格式及状态校验继续适用。

`mutation` 必须匹配 `project-update` 配置；会话必须属于目标项目。当前目标已经包含在固定意图中，不再作为可变项目／任务资料重复放入 `context_refs`。调用方不能在 `context_refs` 中建立 `agent_mutation` 引用；只读引用不等于执行权。

沿用 `GET /v1/runs/{id}`、`GET /v1/runs/{id}/event-log`，在当前可见范围内返回可选 `mutation`：准确参数、原值、意图摘要、状态、业务操作号、结果版本及实际结果。不新增模型批准接口。发送丢失回执时，以原幂等键或原 `client_message_id` 核对；相同消息号更换参数返回冲突，不创建第二项更新。

## 4. 数据与事务

迁移 `0050_agent_run_mutations.sql` 增加两张不可修改／删除的表。

| 表 | 关键内容 | 约束 |
| --- | --- | --- |
| `agent_run_mutations` | run、发起人、会话、项目、准确工具／对象、基础版本／来源摘要、参数字段集合、原值、固定意图及 SHA-256 | 每 run 一项；绑定排队中的项目更新配置及发送者；意图摘要／字段一致；原消息必须引用该固定意图 |
| `agent_mutation_commits` | 原 run、真实业务操作号、结果版本／来源摘要、业务结果 | 每 run 最多一次；结果版本必须为基础版本 +1；匹配成功的业务幂等记录及最终工具回执 |

共六个触发器，其中两个为提交时延迟校验。应用身份只有 SELECT／INSERT 权限，不能重写或删除意图及提交证据。固定意图还包含发起人的授权版本、组织授权版本、会话修订和安全版本，数据库与实际 run 核对。

受理时按项目、任务顺序持有读取锁，保证基础版本与原值来自同一固定状态。真正执行时，在现有短事务及组织／会话／租约校验内复用 `project.Service.Update`、`UpdateTask` 或 `TransitionTask`。业务命令的权限、版本、审计、outbox 和幂等规则照常执行。

内部幂等键固定为 `agent-mutation:{run_id}`，路由键为 `/internal/agent-mutations/{tool}`。模型不能选择键或执行身份。业务修改、业务操作、审计／outbox、提交记录和工具回执共用同一事务；任一证据保存失败，全部回滚。不同工具调用键再次请求同一准确范围，也只返回原提交回执。

序列化保留原 JSON 字段集合：遗漏日期表示不修改，明确 `null` 表示清空。不把带 `Nullable` 的业务 DTO 重新整体序列化后作为补丁，避免把未选字段误清空。

## 5. 不可变来源与执行中的可变对象

新增 `agent_mutation` 来源类型，以 run UUID 标识固定意图；`resource_version` 恒为 1，SHA-256 绑定真实意图内容。它只在原会话和原受众范围内可见，来源正文不是执行授权。历史页面要求当前调用者仍有会话／业务阅读权限；用于模型时，当前全体参与者都必须在原受众内且共同允许阅读／AI 处理。新增成员不能通过模型读取旧更新意图。

执行前及每次工具调用仍核对目标当前状态：未提交时必须等于原基础版本／摘要；已由本 run 提交时必须等于本次真实结果版本／摘要。外部人员在中途修改对象会使本次执行停止，不能以旧决定覆盖新状态。

`read_resource` 读取本次目标时，工具凭证引用 `agent_mutation`，当前正文另带观察摘要／版本。这样本次合法修改不会令自己的前置读取证据自动失效，同时仍保留准确的意图与原／新事实。其他资料继续遵守原严格版本绑定，不整体放宽来源检查。

历史消息读取不要求业务对象永远停在该次结果版本；固定意图与当时提交事实可继续核对，历史页面仍核对当前调用者的会话／业务阅读权限，撤权或不可见时隐藏依赖正文和引用。供模型处理则另核对当前共同受众、AI 分类许可和原受众范围，不把新增成员追溯加入旧消息。

## 6. MCP、原生边界与完成判定

`project-update` 仅暴露五项工具：`read_resource`、`inspect_operation`、`update_project`、`update_task`、`transition_task`。原生隔离证明的工具集合必须精确匹配；没有任意检索、审批、SQL、shell 或外部地址工具。

服务端将固定范围放入 `prepared_context.authorized_mutation`。写工具必须逐项匹配该记录的工具和参数；同样的正文、旧意图或其他 run 不可转移授权。模型不能改用新版本或不同原因，即使新版本碰巧可写。

运行时与后端分别核对完成证据。只有本 run、当前权限戳下允许的实际写工具成功，`committed=true` 且操作号来自真实业务回执，才可返回 `completed`。读取固定意图或 `inspect_operation` 成功只证明观察；不能将其当写入完成证据。
