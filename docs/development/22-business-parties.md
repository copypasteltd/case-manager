# 往来资料与固定业务依据

本模块为 [合同、采购、报销](../requirements/04-workflows-and-oa.md) 与 [费用、订阅](../requirements/05-finance-and-subscriptions.md) 提供共用的相对方/供应方资料底座。当前实现资料管理、不可变修订、权限与 Web 页面；已接入合同草稿的准确修订引用；订单、费用及订阅引用仍需后续接入，不能把资料保存当作业务批准或付款。

## 1. 资料模型

`parties` 保存组织、可选项目、不可变创建人、分类、active/archived 状态、当前资料修订及乐观锁版本。`party_revisions` 保存准确名称、机构/个人类型、supplier/customer/other 关系、联系人、单一邮箱、电话、说明、作者、修订依据及基础修订。

同一个对象可以具有多种关系，不因“既是客户又是供应方”复制金额或自动合并业务。名称不设全局唯一，不能把同名个人或机构误合并；用户须核对准确对象标识。当前没有银行账号、卡号/CVV、自动付款或邮件发送字段。

修订只允许追加，禁止修改或删除。头的当前修订使用同组织、同对象的复合外键，延迟至事务提交核对；基础修订也必须属于准确对象。新增修订序号由被锁定对象的当前修订递增，不能用跨对象 MAX+1 取号。归档/恢复只改变头状态与头版本，不制造内容修订。

数据库触发器保护组织、对象 ID、创建人、项目、分类和创建时间。普通内容编辑不能迁移安全范围；独立分类/范围影响流程尚未完成。当前创建严格受限资料会明确拒绝，要求专门的对象授权流程，不能静默降为普通内部资料。

## 2. 权限与安全范围

新增未绑定角色 `party_manager`，含 `party.read/create/update/archive`；由管理员显式分配组织、项目或本人范围及分类上限。配置管理员没有自动读取客户或供应方内容的权限。往来资料不自动授予项目权限，也不因关联业务而自动授予文件读取权限。

创建要求 create 与 read；项目受限资料必须关联项目，分类不得低于项目。编辑、归档和恢复同时核对 read 与对应动作权限；本人范围以不可变创建人为准。项目 closing/archived/cancelled 时阻断资料写入，当前和历史资料仍按权限可读。

当前资料允许有 read 权限的读者查看；历史修订额外要求 update 权限，避免只读选择器遍历历史联系字段。每个业务后续固定快照时需要以该业务的权限规则明确展示其固定依据，不以资料当前修订覆盖旧快照。

列表在 SQL 中先应用 can_access、项目/关系/状态和名称筛选，再分页。名称查询按字面子串匹配，百分号不是通配符。游标绑定组织、用户、用户/组织授权版本、渠道、Agent 运行及查询条件，历史游标额外绑定准确对象。

## 3. 已实现接口

| 接口 | 约束 |
| --- | --- |
| `GET /v1/parties` | q、state、relationship、project_id、company_only、游标；只返回有权读取的对象 |
| `POST /v1/parties` | 创建头与首个准确修订；联系人等非必要字段可为空 |
| `GET /v1/parties/{id}` | 当前修订内容与当前 can_edit/can_archive/can_read_history |
| `PATCH /v1/parties/{id}` | 完整新内容、expected_version、base_revision_id、reason；空字符串明确清空相应可选联系字段 |
| `POST /v1/parties/{id}/state` | archive/restore、准确头版本与原因 |
| `GET /v1/parties/{id}/revisions` | 受保护的准确对象历史，分页返回 |
| `GET /v1/parties/{id}/revisions/{revision}` | 同组织、同对象的准确修订；不可跨对象错绑 |

命令按组织授权锁、用户、可选项目、往来头的顺序锁定，写入前重新读取版本与权限。内容修订、当前指针、审计、Outbox、幂等结果在一个事务提交；审计失败全部回滚。幂等重放前重新鉴权，撤权后不能取回原成功命令的敏感内容。相同头版本的两个设备编辑最多一个成功。

## 4. Web 与视觉约束

`/parties` 提供名称搜索、关系与状态筛选；`/parties/:id` 展示当前联系资料及对象能力。创建可选有权访问的活动项目；归档资料保留历史且停止普通编辑，恢复不重写原内容。暂存于编辑器的冲突内容保持可读，不能自动重定基础修订再次提交。

沿用 CopyPaste 字体、语义色、面板、圆角和内嵌表单规范。机构/个人图标只辅助识别，关系和归档状态同时用文字表达；联系字段、长名称和说明可换行。小屏筛选重排为单列，详情和修订弹窗允许正常滚动。业务依据使用准确修订 ID；页面文案不把普通联系资料更新表述为合同修订已批准。

## 5. 验证与后续接入

`TestBusinessParties` 的 7 个原生 PostgreSQL 叶场景覆盖默认无绑定、配置管理与内容隔离、只读/本人范围、固定修订、并发编辑、不可变创建人和分类、归档/恢复、审计回滚、项目只读、字面查询、身份绑定游标及重放前撤权。

运行 `python app/scripts/test_backend.py -run '^TestBusinessParties$' -timeout=3m -v` 可复现隔离测试。真实页面脚本为 `node app/scripts/check_parties.mjs`；它只使用明确标记的虚构项目与联系资料，临时授权仅针对该项目，finally 撤销授权并关闭全部自建浏览器。结果及截图保存在 [往来资料证据](../quality/evidence/parties/result.json)，不把本地虚构供应方当公司真实经营数据。最近6条真实检查链通过，含双主题五宽度、历史资料、真实第二设备并发冲突及归档恢复；临时项目授权已撤销，全部自建浏览器已关闭。390px浅色历史与1440px深色详情截图已人工复核。

合同后续需固定相对方修订和正文文件版本；采购订单、报销供应方、订阅 vendor 引用准确对象。归档对象应阻止新的业务选择，但不能使已批准或已签署业务丢失原依据。法律登记信息、复杂地址、付款账户、合并去重、独立安全范围迁移及这些业务引用尚未实现，按明确需求继续接入。

合同草稿通过内部固定依据读取器按准确对象/修订引用联系资料，同时重新核对当前 party.read。公共历史列表仍要求 update；不能利用合同选择器遍历全部历史。company_only 在分页前限制项目为空，禁止同时传 project_id，筛选纳入游标绑定。详见[合同草稿](23-contract-drafts-and-fixed-evidence.md)。
