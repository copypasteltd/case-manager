# 项目交付修订与人工验收

日期：2026-10-24。状态：本地后端与Web实现及验证已完成；完整四端与真实业务仍待验收。关联PM-07/08、WP-04及[项目需求](../requirements/03-projects-and-knowledge.md)。开发位于app/，所有说明及证据位于docs/；不调用本地虚拟化环境。

## 1. 业务契约

交付是独立业务事实。文件上传成功、任务完成或秘书总结均不等于交付通过验收。创建交付草稿时指定名称、验收准则、有效项目负责人及可选里程碑；提交固定1—20个可用正式文件版本、说明、当时的名称／准则／负责人／里程碑及项目分类。每次提交产生新的不可变修订、内容摘要及文件引用，不覆盖旧修订或决定。

状态为draft、submitted、accepted、changes_requested。草稿和退回状态可以修改资料；待验收时不能静默改换文件或准则。退回后重新提交产生新修订；已验收交付明确提交新修订时，旧验收保留，新修订重新等待验收。已达成／取消的里程碑必须先明确重开，才能变更其交付；归档、取消或结项核查中的项目拒绝普通写入。

## 2. 权限与人工决定

沿用deliverable.read/create/submit/decide权限；新增可明确分配的deliverable_reviewer（项目交付验收人）角色，只含read／decide并要求MFA，默认不分配。基础项目角色权限兼容保留，但没有验证器的验收人须由管理员明确分配该角色，再登录完成真实设置；不以额外财务／系统权限换取MFA。草稿编辑使用deliverable.create，创建人永久固定，不随负责人转移而扩大本人范围。列表只返回获准对象；详情和修订重新检查当前项目与文件权限，不以业务资料授权替代文件授权。不完整的文件依据不允许提交或验收。

提交和决定使用真实交互会话；验收决定另要求近期MFA、准确交付版本、准确修订ID及内容摘要。通过验收须逐项人工确认完整文件和准则，且验收人不得是该修订提交人；这是产品派生的默认独立核验规则。退回说明必须明确，初始不预选任何决定或声明，AI／TG身份不能代替人工验收。

## 3. 事务与历史

事务先锁项目、再锁交付，核对版本、状态、里程碑及文件依据。提交／决定、头版本、不可变文件引用、审计、outbox和幂等同事务提交；幂等重放前仍核对当前授权、实际会话及完整文件读取能力。并发两次验收最多成功一次；外部新修订使旧决定拒绝，不能自动换新版本重试。

迁移0044扩展已有交付表，保存准确提交内容和决定会话，增加新协议的一致性及不可变保护。既有缺少来源信息的记录保持旧协议，不补造提交人或验收人；不得把旧记录自动升级为已核实的新协议记录。

## 4. 页面与验证要求

项目新增交付页签，沿用官网暖白／蓝灰黑、墨色主操作和品牌蓝来源链接。页面明确区分草稿、待验收、退回及已验收；详情展示当前资料、每次修订和对应决定。提交使用准确文件版本选择器，验收显示固定准则、文件及完整人工声明；版本冲突保留说明、文件和选择，禁止再次提交旧依据。

验证须覆盖首次提交、退回重提、固定历史、已验收后新修订、不可自验、真实MFA／自动身份、文件读取及业务撤权、无效文件、并发唯一决定、审计回滚、SQL约束、里程碑冻结及项目只读。真实Web/API检查须关闭所有自有浏览器与不用的标签，记录明暗主题和五档宽度。移动交付、真实云文件及完整项目财务结项继续按原首发门禁验收；本页不是通过证据。
