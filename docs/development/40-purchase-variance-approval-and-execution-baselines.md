# 采购差异重审与执行基线

日期：2026-10-24。状态：本地实现及第8节所列验证通过，完整多端与外部验收继续。依据[OA-10](../requirements/04-workflows-and-oa.md)及[采购履行协议](34-purchase-orders-acceptance-and-returns.md)。本章增加独立差异提案、准确顺序审批和显式启用；原商业批准及既有订单／验收事实继续保留。

## 1. 业务与审批

原采购继续保存准确商业批准。差异提案固定原采购、生效执行基线、采购版本、当时履行集合及完整拟执行内容，逐项展示原依据与变更。币种、税费计算方式、原始行身份／描述／单位保持；数量、单价、税／折扣上限与供应商候选可按明确制度重审。新增物品使用新采购，不能伪装为旧批准行。

使用独立`purchase_variance`业务类型与已发布规则选择；不存在适用制度时阻断，不自动借用普通采购批准，不设置未经确认的默认容差。顺序步骤、指定人员、本人审批制度、MFA、撤回／退回／拒绝和准确快照遵循共用申请协议。原执行基线在提案获批及明确启用前继续有效。

## 2. 启用与后续执行

启用须具备独立授权、实际人工会话与近期MFA，固定准确批准提案、原采购版本和执行基线。下单、验收、取消或其他执行基线已变化时，旧提案不能静默生效；须重新核对并重审。新上限不得小于已有有效承诺及规范费用。新基线只约束后续订单，旧订单保留当时固定单价、供应商及依据。

全部有效订单继续共同占用当前基线数量／金额／税额／折扣上限。真实费用按当前获批并启用的支出额度校验；原批准金额、执行额度、费用发生和实际付款分别显示。启用不产生供应商订单、验收、费用、银行付款或采购完成事实。

## 3. 业务对象、状态与精确计算

`purchase_variances`是独立业务头，编号使用`CP-PV-`。`purchase_variance_revisions`保存完整不可变内容、固定依据、逐行计算结果和总额。原采购商业修订及批准申请不被新提案替换。草稿也保留完整原行和可计算的新额度；未知数量／单价不能通过差异提案构造未知执行额度。

| 对象／字段 | 约束 |
| --- | --- |
| 原采购 | 必须已批准且未取消，提案沿用同一项目和分类 |
| `basis` | 固定采购 ID／版本、原批准修订／摘要、当时执行基线修订、完整内容／金额／逐行值及履行集合 |
| 内容摘要 | 包含提案身份、范围、完整拟执行内容、basis、逐行值和金额的规范 JSON 摘要 |
| 商业修订 | 固定基版，序号连续；不能覆盖审批中或获批修订 |
| 生命周期 | `draft`、`requested`、`effective`；审批状态独立沿用共用申请协议 |
| 启用事实 | `purchase_plan_activations`固定提案修订、准确批准申请修订、采购执行版本、真实人工会话／MFA／原因 |
| 文件引用 | `purchase_variance_files`固定新旧内容引用的完整正式版本并集，写入不可变引用登记 |

保留全部原行身份、描述、单位、币种、计价及舍入规则；允许调整数量、单价、税额、折扣及供应商候选。金额使用现有精确十进制与币种精度，数据库按完整输入独立重算逐行金额和总额。不能提交自由文本“追加预算”作为可执行额度。新增商品／服务行另建采购。

## 4. 独立申请与明确修订

共用申请、送审预览、固定制度、顺序决定、退回／撤回／拒绝及历史读取协议增加`purchase_variance`适配。普通`purchase`和`claim`商业入口仍仅接受原有两种业务类型。差异制度按真实类型、类别、币种和金额匹配，必须独立发布；所有差异都需明确审批，不预设未经确认的免审阈值。

完整申请快照包含`purchase_variance`依据、拟执行内容、逐行值、总额以及新旧供应商／文件版本证据。读者按当前权限重新投影证据。申请、审批队列在 SQL 分页前同时核对父采购和提案权限，撤销父采购访问后不能通过申请标题、列表或历史旁路读取。

发生新订单、验收、取消或其他基线启用后，旧提案的固定采购版本过时。可编辑提案须由用户明确核对当前执行内容并保存新商业修订，随后更新申请草稿并重新审批。旧商业修订和旧审批决定继续保留。已获批但过时的提案不能直接编辑，须另起准确提案。

## 5. HTTP 契约与客户端一致性

具体字段以[同源 OpenAPI](openapi.json)为准。新增8项操作，读取遵循当前父对象和资源范围；写入遵循共同幂等、审计及错误协议。

| 方法与路径 | 用途／输入 |
| --- | --- |
| `GET /v1/purchases/{id}/execution-plan` | 原批准或最新已启用完整执行内容、采购版本、来源、当前可见供应商／文件证据 |
| `GET /v1/purchases/{id}/variances` | 当前有权查阅的分页提案 |
| `POST /v1/purchases/{id}/variances` | 完整拟执行内容、固定采购版本／执行基线、原因 |
| `GET /v1/purchase-variances/{id}` | 提案、固定 basis、当前动作能力及证据 |
| `PATCH /v1/purchase-variances/{id}` | 准确提案版本／商业基版、完整新内容及明确核对后的当前采购依据 |
| `GET /v1/purchase-variances/{id}/revisions` | 有权管理者的分页商业历史 |
| `GET /v1/purchase-variances/{id}/revisions/{revision}` | 精确不可变商业修订，重新投影今日权限 |
| `POST /v1/purchase-variances/{id}/activate` | 准确提案版本／修订／摘要、固定采购版本、原因及实际近期人工 MFA |

订单输入增加`execution_plan_revision_id`，保存登记时的准确基线。最初沿用原批准时可省略／为 null，以兼容已有客户端；一旦启用差异基线，省略或传其他基线都会拒绝。即使原采购商业摘要未变化，也不能凭旧订单表单绕过当前执行依据。

执行历史增加`plan_activated`和准确差异商业修订。原商业批准金额继续只表示原批准；履行汇总中的额度字段表示当前执行基线上限。客户端明确区分这两个口径，不能用相同“批准金额”标签掩盖来源。

## 6. 事务、费用与数据库保护

启用先执行当前授权和真实人工会话检查，随后按项目、父采购、提案、相关费用 ID 顺序加锁。锁定后重新读取准确版本、固定依据和批准申请；所有来源都正确才写入不可变启用事实、采购履行事件、采购版本推进及提案生效状态。审计、幂等回执与上述变更在同一事务提交，任一失败全部回滚。

同一父采购的并发提案启用只有一个能使用原版本。真实 MFA 必须来自未过期、未撤销、用户仍有效且认证版本一致的数据库会话，不能相信调用方传入的时间；AI／自动运行身份不能启用。幂等重放也先重验当前授权与实际会话证明。

有效订单累计数量、金额、税额和折扣不得高于当前基线，降低额度不得低于既有有效承诺。旧订单按它登记时的基线核对供应商、价格和计算，不能用新价格重算。连续启用的新基线也遵循相同规则；收货、原来源退货、取消余量和履行时间顺序继续使用既有保护。

关联真实费用在原币和原采购准确商业修订上保留归属。费用关联／确认按当前已启用额度校验。启用时锁定并重新核对全部关联费用；无法完整读取时阻断，不能把不可见费用当作零。即使费用在提案获批后新增、且采购版本未改变，额度仍不得低于当下有效实际费用。

迁移0041扩展独立制度类型、启用事件和订单来源；旧迁移不改写。延迟约束保护连续商业修订、头／申请一致、完整文件引用、执行时间顺序、历史价格和累计上限；即时约束保护新修订的当前依据及实际启用会话。应用仅可新增不可变历史，不可更新／删除。文件来源凭证、计算和会话的 SQL 反例测试需独立拒绝，不能只测试 HTTP 校验。

## 7. 权限与页面交接

新增默认未绑定角色：`purchase_variance_manager`（提案查阅／创建／修改及父采购查阅）、`purchase_variance_reader`（仅提案查阅）、`purchase_plan_activator`（父采购／提案查阅及启用，要求 MFA）。提案读者仍必须另有父采购访问；审批者必须具备准确业务内容和证据的当前读取权限。迁移和启动不会自动为员工赋予新角色。

Web 采购详情增加当前执行依据与差异列表，独立提案详情提供完整前后对照、送审、明确启用和商业历史。订单表单读取并固定最新执行基线，保留旧原采购商业批准身份。冲突不覆盖输入，也不自动重试成最新版本。[页面设计](../design/13-purchase-variance-and-execution-baselines.md)约束状态名称、颜色、操作顺序及四端表达。

Taro 微信／抖音／Android共用申请快照增加完整依据、原承诺及拟执行内容展示，沿用现有审批。移动采购管理、原生宿主和真实平台验收继续实施；不能把共用快照适配写成完整移动采购闭环。
