# 可行性评估与总体建议

日期：2026-10-22。版本：v0.2。状态：已纳入用户补充，供立项讨论；服务器规格、预算和审批细则待确认。

## 1. 评估结论

**整体技术上可行，建议按“统一业务底座、项目档案、受控 AI 秘书、多端入口、跨云恢复”推进。** Go、PostgreSQL、React/Vite 能覆盖主要管理需求；Taro 可承担移动端；对象存储适合文件原件与版本存储。主要难点集中在跨角色权限、AI 写入可靠性、120 GB 文件传输、双云数据一致性、移动端适配和长期运维。

已确认基线：3 名员工、3 人同时在线，人员在香港，云服务器位于境内；原件约 2 TB、最大单文件 120 GB。Web、微信小程序、抖音小程序、Android 必须首发；大文件由 Web/Android 上传，小程序负责查阅与审批。业务为合同、报销、采购、月度开支/订阅和完整项目管理，不做考勤、人事。

AI 部分具有上线前置条件：当前 OpenAI 官方 API 支持地区列表未列出香港和中国大陆。必须根据公司账号、实际服务提供与使用地区、选定产品及供应商条款确认资格。将服务器迁到支持地区本身不能证明业务有使用资格。这个判断来自官方支持列表，不代表已经对你司具体账号作出结论。[官方支持地区](https://developers.openai.com/api/docs/supported-countries)

因此，可立刻规划和实施基础业务系统；对“官方 Codex 服务可直接覆盖所有员工”的承诺，应等待资格核实。若资格无法满足，保留相同的业务工具与流程，另行评估在目标地区可用的模型和运行时；该替代路线不应被表述为原生 Codex 已经落地。

## 2. 对公司背景的理解

通过原生 HTTPS 读取 [CopyPaste 官网](https://copypaste.hk/) 成功，页面主要介绍 AI 应用与知识平台、跨境网络、支付协作相关能力。以下规划据此将内部工作组织为“客户/合作方 → 项目 → 交付内容 → 文件/知识 → 服务运行状态”。这属于系统设计推导，不代表已经了解你司组织架构、客户规模、资金业务或现有内部系统。

系统可作为公司自身运营平台，并为后续展示交付能力积累经验。首期按内部自用设计；未来若向客户提供多租户产品，应另做租户隔离、计费、合同和产品化评估。

## 3. 原始设想与建议调整

| 原始设想 | 评估 | 建议落地方式 |
| --- | --- | --- |
| 一个 Go + PostgreSQL 总后端 | 适合当前方向 | 模块化单体承载统一权限和业务；API、后台任务可分进程运行 |
| 后端、前端都在同一台服务器 | 初期可行 | React/Vite 构建后由 Web 服务器托管静态资源；数据库独立持久化；AI 进程有单独资源限制 |
| 多用户、多权限、项目与文件管理 | 可行但属于底座工作 | 统一组织身份、项目成员、资源权限、敏感级别、审计和离职回收 |
| React 管理端 + Taro 小程序/App | 可行，需要分别适配 | Web、微信、抖音、Android 同批首发；复用 API 和业务逻辑，分别做真机与发布验收 |
| 基于 Codex 构建在线总秘书 | 有条件可行 | 独立运行时接入；每个用户/群话题拥有隔离上下文；操作由 Go 业务层授权执行 |
| 秘书能够读写全部文件与目录 | 业务能力可覆盖，权限需要定义 | 对公司授权纳管的资料提供文件级读写；每次以调用人或明确授权的自动化身份执行 |
| 预置文件更新、项目创建、资料整理 Skill | 可行，且是核心交付内容 | Skill 配合结构化工具、数据库事务、版本检查和审计；不能仅靠提示词实现可靠流程 |
| 股东 TG 群实时沟通 | 可行 | Bot Webhook 接入同一会话平台；绑定身份；限定可在群内公开的数据范围 |
| OSS + R2 两地备份 | 可实现跨云副本；地理边界另核实 | 支持 120 GB 分片与断点续传；单主存储 + 异步复制 + 校验 + 不同步硬删除 + 恢复演练 |
| 服务器本地只保留临时数据 | 应用节点可做到 | PostgreSQL、审计、会话和任务状态必须放在独立持久化服务；Codex 本地状态单独处理 |

## 4. 必须提前解决的四个结构问题

### 4.1 “同一台服务器”与“本地只有临时数据”

PostgreSQL 的活动数据目录属于持久化数据库，不能作为可随时删除的缓存；对象存储也不适合作为 PostgreSQL 活动数据盘。推荐将“同一台服务器”理解为应用与前端共用现有境内计算节点，数据库使用独立托管 PostgreSQL。现有服务器规格后续提供，暂不推定已有数据库或足够跨境带宽。

如果必须自建 PostgreSQL，就需要为数据库单独配置持久化磁盘和备份，并明确“本地仅临时数据”只约束应用节点。两种方案都可实施，但不能同时承诺数据库本地落盘和本机所有数据随时可丢弃。

### 4.2 “公司总秘书”与“所有人共享同一权限”

对外表现为同一个秘书，内部应拥有多个会话、任务和执行身份。员工查询资料时遵守该员工的业务权限；定时整理使用有固定范围的服务身份；股东群查询受群公开范围限制。

具备文件操作能力，不等于每个提问者都能借秘书读取薪酬、股东材料或其他项目。权限必须由业务后端执行，并覆盖检索结果、文件下载、引用、摘要和会话历史。

### 4.3 Codex 的“可集成”与“可直接承诺生产稳定性”

官方提供 Codex SDK 用于程序化控制本地 Agent；app-server 提供自定义客户端集成协议。但截至本次核实，app-server 文档仍将命令及 WebSocket 相关能力标为实验性质，不能直接把它当成有稳定生产支持承诺的基础设施。[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)、[app-server](https://learn.chatgpt.com/docs/app-server)

建议 PoC 优先验证 SDK 的有界任务与流式事件，管理系统自行保存会话和审批状态；app-server 作为增强会话体验的候选适配器。是否进入生产由隔离、恢复、升级兼容性测试决定。若不能满足，基础业务继续运行，AI 适配路线单独决策。

### 4.4 双云副本与可恢复备份

OSS 原生跨区域复制针对 OSS Bucket，不能直接视为 OSS 到 R2 的自动复制能力。R2 的 Location Hint 是尽力放置提示，不能据此承诺备份位于某个具体城市。[OSS 复制范围](https://www.alibabacloud.com/help/en/oss/user-guide/cross-region-replication-overview/)、[R2 数据位置](https://developers.cloudflare.com/r2/reference/data-location/)

备份还必须包括 PostgreSQL、权限、文章正文、会话、审计和恢复配置。仅复制附件，无法恢复完整管理系统。需要明确副本延迟、保留期、恢复清单、管理员凭据隔离，以及恢复时数据库引用与文件版本是否匹配。

## 5. 可行性分项

| 维度 | 判断 | 主要依据与条件 |
| --- | --- | --- |
| 业务适配 | 可行 | OA、项目、文件、知识和状态具有共同的身份与项目上下文 |
| 技术实现 | 可行 | 常见 Web 系统架构，初期不需要微服务平台 |
| AI 集成 | 有条件可行 | 服务资格、运行时稳定性、工具权限、文件格式和正确率均需验证 |
| 多端接入 | 可行 | API 可复用；微信、抖音小程序和 Android 分别适配、审核/分发与验收 |
| 文件与恢复 | 可行 | 跨云复制需自建或集成任务；应用级版本和一致性校验不可省略 |
| 单机部署 | 适合试点 | 存在应用单点；监控、数据库和备份不能全依赖该节点 |
| 运维可持续性 | 取决于投入 | 需要明确负责人、告警、补丁、恢复演练和 AI 成本管理 |
| 预算与周期 | 可估算，待参数收敛 | 以明确范围和 PoC 结果估算；不能从技术栈直接推导固定报价 |

## 6. 推荐方案

采用“一个业务平台、多个访问入口、独立秘书运行时、两个文件存储副本”的形态：

1. **统一业务后端**：组织与权限、项目、文件目录与版本、项目博客/OA、状态汇总、通知、审计、任务调度。
2. **管理门户**：React + Vite，是完整管理入口；移动端聚焦待办、审批、查询、轻量文件操作和秘书会话。
3. **AI 服务层**：受控执行既有业务 API；技能、任务与可见会话状态可追踪；可暂停写入而保留查询。
4. **持久化层**：独立 PostgreSQL 保存业务事实；OSS/R2 保存文件原件、文件版本与独立备份。
5. **运维层**：外部探测、状态新鲜度、审计、复制延迟、任务失败、预算阈值和恢复演练。

所有部署和本地验证按原生进程设计；遵守当前约束，不调用本地 Docker、WSL 或其他本地虚拟化环境。移动端使用真机验证。

## 7. 自建范围与复用策略

| 能力 | 推荐 |
| --- | --- |
| 项目档案、公司流程、权限、秘书工具 | 自建，体现你司实际工作方式 |
| 数据库、高可用、备份基础设施 | 优先托管服务，按资格和预算选型 |
| 文件存储 | 使用 OSS/R2，封装适配层与复制任务 |
| 指标采集与告警 | 复用成熟监控服务或原生监控组件，不重写采集器 |
| 文档预览与 Office 编辑 | 分阶段；先预览、下载和替换版本，再评估专用编辑器的许可与运维 |
| OA 引擎 | 首期固定流程和显式状态机；流程数量与复杂度上升后再评估通用引擎 |

## 8. 建议的立项边界

首发覆盖：账号权限、完整项目业务闭环、合同全生命周期、报销、采购、月度开支/订阅、文件目录/版本/搜索、项目日志、秘书核心 Skill、TG 群入口、服务状态、120 GB 上传/复制和恢复验收；同时交付 Web、微信小程序、抖音小程序和 Android。各端按场景分工，大文件上传由 Web/Android 完成，小程序提供查阅和审批。

内部开发可以先完成 Web 集成，但不能把 Web 单端上线视为已满足首发要求。后续扩展可覆盖更复杂自动化、文档格式操作、故障协作和容量扩展。多人实时 Office 编辑、资金执行、自动服务器变更、客户多租户等应作为独立需求明确后再纳入排期。

3 人规模降低的是在线业务吞吐，不能降低 2 TB 迁移、120 GB 续传和境内外传输的工程要求。应优先用完整大文件 PoC 验证链路与账单，再确定存储主副本和上传策略。

“Codex 部署在服务器”指 Agent 编排、技能和工具运行在自有节点。若采用云模型，必要上下文仍会发送给模型服务商，不等于模型权重在本机推理或所有数据从不离开服务器。需要本地推理时，应另行评估模型与算力路线。[Codex 平台说明](https://developers.openai.com/blog/codex-as-a-platform)

详细工作量、阶段和预算模型见 [实施计划](05-delivery-plan-and-budget.md)。建议先批准范围明确的 PoC 与业务调研，再根据证据冻结正式开发范围。
